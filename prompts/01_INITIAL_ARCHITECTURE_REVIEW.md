# SMART-LOGISTICS AMR — 초기 아키텍처 검증 및 구현 착수 준비

> **작업 단계:** P0 — 승인된 아키텍처 검증 및 구현 준비  
> **아키텍처 상태:** v1.0 승인  
> **승인권자:** A — 윤현수 (팀장)  
> **실행 방식:** 읽기 전용 조사 및 검증 보고  
> **실제 코드 변경:** 금지

## 1. Task — 작업 목표

너는 Ubuntu 24.04 / ROS2 Jazzy·Nav2 기반 물류 AMR 시스템의 수석 시스템 아키텍트이자 통합 검증 전문가다.

프로젝트명은 **SMART-LOGISTICS AMR**이다.

현재 프로젝트의 최종 기획 제안서와 초기 아키텍처 v1.0은 팀장 승인을 받은 상태다.

이번 작업은 아키텍처를 처음부터 다시 설계하는 것이 아니라, 승인된 구조가 실제 구현 가능한지 검토하고 5명의 팀원이 독립 개발을 시작할 준비를 완료하는 것이다.

**핵심 목표**

1. 현재 저장소 및 개발환경 확인
2. 승인된 아키텍처와 최종 기획서의 일치 여부 검토
3. 5개 ROS2 패키지 및 웹 모듈의 책임 경계 검증
4. 모듈 간 필수 데이터 계약과 미결정 사항 식별
5. MOCK / SIM / REAL 환경 적용 가능성 확인
6. 실차 Gate 0~2 검증 준비 사항 정리
7. 팀원별 병렬 개발 착수 작업 도출

이번 요청에서는 실제 구현이나 파일 수정을 수행하지 않는다.

## 2. Context — 프로젝트 기준

### 2.1. 최상위 문서

다음 우선순위를 적용한다.

1. `docs/reference/ORIGINAL_PROPOSAL.md` — 2026.11.17 최종 기획 제안서
2. `AGENTS.md` — Codex 공통 개발 규칙
3. `docs/PRD.md` — 승인된 기획의 핵심 요구사항
4. `docs/ARCHITECTURE.md` — 승인된 초기 아키텍처 v1.0
5. `docs/INTERFACES.md` — 공통 인터페이스 설계 기준과 세부 후보
6. `docs/SIM_TO_REAL.md` — 실차 검증 계획 및 안전 기준
7. `docs/DECISIONS.md` — 기술 결정과 변경 기록
8. `docs/reference/CODEX_FULL_BRIEF.md` — 과거 상세 설계 요구를 확인할 때만 참고

`ORIGINAL_PROPOSAL.md`는 실제 최종 기획서로 교체된 상태다. 더 이상 재구성본이나 원문 미확보 상태로 취급하지 않는다.

`CODEX_FULL_BRIEF.md`와 이전 프로젝트 자료에 과거 역할 분담이나 상충하는 지시가 남아 있다면 최종 기획서와 승인된 아키텍처를 우선한다. 단, 기획서 이후 팀에서 승인한 Humble → Jazzy 개발환경 변경은 `docs/DECISIONS.md`의 해당 결정에 따른다.

문서 충돌이 발생하면 실제 파일을 임의 수정하지 말고 충돌 내용과 수정 권고를 보고한다.

### 2.2. 최종 팀원 역할

| 담당 | 이름 | 책임 |
|---|---|---|
| A | 윤현수 | Mission Manager, 상태 머신, 재계획 적용 정책, 통합 |
| B | 정지호 | A*·Dijkstra 전역 경로 탐색 연구 |
| C | 이현수 | 방문 순서 최적화, 동적 재계획 계산, 하드웨어·Bringup |
| D | 홍근태 | Nav2·AMCL, DWB·RPP, 자율주행 및 정밀 정렬 |
| E | 강연주 | FastAPI, SQLite, 웹 관제 및 실험 데이터 |

**C는 물류 최적화와 하드웨어·Bringup을 모두 담당한다.**

B의 전역 경로 탐색, C의 방문 순서 최적화, D의 로컬 주행 제어는 서로 구분된 연구 영역이다.

### 2.3. 확정된 개발 방향

- TurtleBot3 Waffle Pi 1대 사용
- Ubuntu 24.04 LTS / ROS2 Jazzy / Nav2 / Gazebo Harmonic
- HOME 및 작업 지점 A~D 구성
- 작업자 수동 물품 인계
- Job·TaskStep·Waypoint 분리
- Nav2 계획 경로 비용 기반 방문 순서 최적화
- 실제 주행 데이터 기반 검증
- 기본 동적 재계획은 P0 필수
- 재계획 계산은 C, 실행 적용은 A
- TurtleBot3 실차의 OS·드라이버·OpenCR 펌웨어 Jazzy 호환성은 검증 전 항목으로 유지
- 2027.01.15 최종 발표

## 3. Reference — 검증 대상

### 3.1. Monorepo 및 패키지 구조

승인된 기본 구성은 다음과 같다.

| 패키지 | 담당 |
|---|---|
| `logistics_msgs` | A 관리, 공통 |
| `mission_manager` | A |
| `route_optimizer` | C |
| `amr_navigation` | D |
| `amr_bringup` | C |
| `web_control` | E |

패키지가 이미 존재하는지, 추가 생성이 필요한지 현재 저장소를 읽기 전용으로 확인한다.

전역 플래너 연구를 위한 독립 ROS2 패키지는 필수로 가정하지 않는다.

### 3.2. 핵심 인터페이스

다음 책임 경계를 검증한다.

- E → A: 신규 작업 및 인계 요청
- A → C: 방문 순서 및 재계획 요청
- C → A: 방문 순서·예상 비용·기준 계획 버전
- A → D: 승인된 목표 이동 요청
- D → A: 주행 결과 및 준비 상태
- C → Nav2: `ComputePathToPose`를 통한 계획 경로 계산
- B ↔ D: 전역 플래너 설정·실차 검증
- B → C: 경로 계산 기준 및 플래너 선정 결과
- C Bringup → D: 센서·TF·구동환경
- A → E: 미션·작업 상태
- B·C·D → E: 실험 결과

실제 Topic·Service·Action 이름과 사용자 정의 필드는 `INTERFACES.md`의 확정·미확정 구분을 따르며 임의로 표준화하지 않는다.

### 3.3. 데이터 모델

다음 항목의 책임과 관계를 확인한다.

- Job
- TaskStep
- Waypoint
- Mission
- RoutePlan
- RobotStatus
- ExperimentResult

특히 작업 완료 판정, 선후 관계, 계획 버전, 중복 인계 요청 및 오래된 재계획 결과의 처리 방식을 검토한다.

### 3.4. Sim-to-Real

- MOCK / SIM / REAL 구분
- `use_sim_time`과 DDS·네트워크 격리의 차이
- TF·Odometry·AMCL·Lifecycle 검증
- C의 Hardware/Bringup Readiness
- D의 Navigation Readiness
- A의 Mission Execution Readiness
- Gate 0~5의 완료 기준
- 실차 비상정지 및 복구 절차

### 3.5. 우선순위

P0에는 다음이 포함되어야 한다.

- 기본 하드웨어·Bringup
- Nav2 단일 목표 주행
- 다중 작업 상태 머신
- 계획 경로 이동 비용표
- 최적 방문 순서
- 물품 인계 확인
- HOME 복귀
- A*·Dijkstra 연구
- FIFO·Greedy·완전탐색 연구
- 기본 동적 재계획

DWB·RPP 비교는 P1 핵심 연구로 유지한다.

## 4. Evaluate — 검증 기준

다음 조건을 평가한다.

1. 5명이 독립적으로 개발할 수 있는가?
2. 모듈 간 책임 충돌 또는 누락이 없는가?
3. C의 두 업무가 서로 불필요하게 결합되지 않았는가?
4. Nav2 표준 기능을 재구현하고 있지 않은가?
5. A가 미션 상태를 일관되게 관리할 수 있는가?
6. 신규 주문 시 현재 작업을 보호할 수 있는가?
7. Gate 0~2 실차 검증을 시작할 수 있는가?
8. MOCK을 이용한 병렬 개발이 가능한가?
9. P0 핵심 기능이 개발 일정 내 통합 가능한 구조인가?
10. 구현 전 결정해야 할 기술 세부사항은 무엇인가?

검증 결과를 다음 상태로 구분한다.

- `[확인 사실]`

- `[미확인]`
- `[추가 결정 필요]`
- `[수정 권고]`
