# Sim-to-Real 실행 및 실차 검증 기준 — SMART-LOGISTICS AMR

> **문서 상태:** 초기 실차 검증 운영 기준 v1.0  
> **승인권자:** A — 윤현수 (팀장)  
> **기획 기준:** 2026.11.17 최종 기획 제안서  
> **관련 문서:** `PRD.md`, `ARCHITECTURE.md`, `INTERFACES.md`  
> **실제 장비 검증 상태:** 미확인 항목은 별도 표시

본 문서는 SMART-LOGISTICS AMR의 MOCK·SIM·REAL 실행환경, TurtleBot3 기본 구동, Nav2 주행 준비 상태, 실차 검증 Gate 및 안전 절차를 정의한다.

문서 승인과 실제 로봇 검증 완료는 별개다. 테스트를 수행하지 않은 항목은 PASS로 처리하지 않는다.

---

## 1. 검증 목표

1. 하드웨어·ROS2 Bringup이 정상적으로 작동하는지 확인한다.
2. 센서·TF·Odometry·통신이 Nav2 주행에 적합한지 검증한다.
3. 실제 로봇이 단일 목표에 안정적으로 도달하는지 확인한다.
4. 다중 지점 이동 및 HOME 복귀를 검증한다.
5. 웹·Mission Manager·Route Optimizer·Nav2를 통합한다.
6. 신규 주문에 따른 기본 동적 재계획을 실차에서 검증한다.
7. 실험과 실제 주행 데이터를 재현 가능한 방식으로 기록한다.

**최우선 성공 기준은 실제 TurtleBot3의 안정적인 이동과 기본 물류 미션 완수다.**

시뮬레이션의 정상 동작을 실차 검증의 대체 증거로 사용하지 않는다.

---

## 2. 담당자 및 책임

| 담당 | 이름 | Sim-to-Real 책임 |
|---|---|---|
| A | 윤현수 | 통합 실행 승인, 미션 상태·안전 조건 관리, 시험 일정 조율 |
| B | 정지호 | A*·Dijkstra 설정과 전역 경로 실험 검증 |
| C | 이현수 | 하드웨어 전체, 센서·드라이버·TF·통신·Bringup, 계획 경로 비용표 |
| D | 홍근태 | AMCL·Nav2·Controller·실제 목표 이동·주행 안정화 |
| E | 강연주 | 웹 관제, 상태 표시, 로그 및 실험 데이터 관리 |

### 2.1. C — 하드웨어 및 Bringup 전담

C는 실제 TurtleBot3의 기본 동작환경을 구성하고 관리한다.

- 로봇 본체·구동 장치·배터리 점검
- LiDAR·카메라 장착 및 간섭 확인
- 바스켓·물품 모형·마커 준비
- 모터·센서 드라이버 구동
- ROS2 Humble 및 TurtleBot3 Bringup
- 기본 TF와 Odometry 제공 상태 확인
- PC·로봇 네트워크 및 DDS 설정
- 기본 실행 Launch와 복구 절차 관리

C의 담당 범위는 기본 구동 환경까지이며, Nav2 Planner·Controller의 주행 성능 튜닝은 D가 담당한다.

### 2.2. D — Nav2 및 자율주행 전담

D는 C가 제공한 기본 구동 환경을 활용하여 주행 기능을 구현·검증한다.

- AMCL 및 지도 기반 위치 추정
- Nav2 Lifecycle 상태
- Planner·Controller 및 Costmap 설정
- 목표 지점 이동
- 장애물 대응 및 주행 실패 처리
- 도착 판정 및 주행 피드백
- DWB·RPP 비교
- 필요 시 도착 정밀 정렬

D는 센서·TF·Odometry의 문제가 발생하면 C와 공동으로 원인을 확인한다.

### 2.3. A — 통합 실행 관리

A는 다음 사항을 담당한다.

- 실차 테스트 일정과 장비 공유 조율
- 미션 실행 조건 검사
- Readiness 결과와 미션 상태 연동
- 주행 요청의 승인·차단
- 오류 발생 시 미션 상태 관리
- Gate별 검증 결과 취합

A의 소프트웨어 실행 승인 기능이 물리적인 안전 정지 장치를 대신하지는 않는다.

## 3. 실행환경 분리

### 3.1. MOCK

**목적:** 실제 로봇 없이 물류 업무 로직과 데이터 계약 검증

검증 대상:

- Job·TaskStep 상태 전이
- 방문 순서 최적화
- 신규 주문 재계획
- 계획 버전 검사
- 물품 인계 확인
- 웹과 Mission Manager 연동

MOCK의 성공은 실제 주행 가능성을 의미하지 않는다.

### 3.2. SIM

**목적:** Gazebo 및 Nav2를 이용한 주행·통합 검증

검증 대상:

- 지도 및 가상 센서
- TF·Odometry
- Nav2 목표 이동
- 경로 계획과 장애물 반응
- 다중 지점 미션
- 알고리즘 비교

시뮬레이션 실행 시 ROS 시간과 통신 영역을 실제 로봇 환경과 혼동하지 않도록 설정한다.

### 3.3. REAL

**목적:** 실제 TurtleBot3의 안전성과 물류 미션 완성도 검증

검증 대상:

- 실제 센서·구동 장치
- 네트워크 연결
- TF·Odometry·AMCL
- Nav2 목표 이동
- 실제 주행 거리·시간·오류
- 물품 인계 및 HOME 복귀
- 신규 주문 동적 재계획

실험 결과에는 실행환경을 반드시 기록한다.

## 4. 환경별 설정 및 격리

| 항목 | MOCK | SIM | REAL |
|---|---|---|---|
| 로봇 | 가상 상태 | 시뮬레이터 로봇 | 실제 TurtleBot3 |
| 센서 | Mock 데이터 | 시뮬레이션 센서 | 실제 센서 |
| 시간 기준 | 구성에 따라 결정 | 일반적으로 시뮬레이션 시간 | 실제 ROS 시스템 시간 설정 확인 |
| Nav2 | Mock 또는 미사용 | 시뮬레이션 Nav2 | 실제 Nav2 |
| 제어 출력 | 실차 명령 불가 | 가상 로봇 대상 | 승인된 실제 로봇 대상 |
| 데이터 기록 | Mock | SIM | REAL |

### 4.1. `use_sim_time`

`use_sim_time`은 ROS 노드의 시간 기준을 설정하는 기능이다.

SIM에서는 `/clock` 기반 사용을 검토하고, REAL에서는 실차 시스템과 일치하는 시간 기준을 확인한다.

`use_sim_time`만 설정했다고 실제 로봇과 시뮬레이션의 DDS 통신이 격리되는 것은 아니다.

### 4.2. DDS 및 네트워크

다음 항목을 실행환경별로 확인한다.

- `ROS_DOMAIN_ID`
- DDS 구현체 및 관련 환경변수
- 개발 PC와 로봇의 네트워크
- 실제 사용 Topic 및 노드
- 실행환경 간 의도하지 않은 통신 여부
- 중복 `/cmd_vel` Publisher 존재 여부

실제 Domain ID 및 로봇 IP 주소는 장비 확인 후 기록한다.

실차 제어 환경에서는 불필요한 시뮬레이션 노드가 주행 명령을 발행하지 않도록 한다.

### 4.3. 실행 프로파일

[설계 후보]

MOCK / SIM / REAL별 실행 Launch·설정 파일을 구분한다.

환경별 차이가 불필요하게 Mission Manager의 비즈니스 로직으로 확산되지 않도록 한다.

## 5. Readiness 검증 구조

실차 자동 주행 전 다음 세 영역의 준비 상태를 확인한다.

| Readiness | 담당 | 검증 영역 |
|---|---|---|
| Hardware/Bringup | C | 센서·드라이버·TF·통신·구동환경 |
| Navigation | D | AMCL·Nav2·Planner·Controller·위치 추정 |
| Mission Execution | A | 작업 상태·목표·안전 조건·실행 권한 |

### 5.1. 상태값

| 상태 | 의미 |
|---|---|
| PASS | 필수 항목을 검증해 정상으로 확인 |
| FAIL | 필수 항목에서 이상 또는 실패 확인 |
| UNKNOWN | 필요한 정보를 확인하지 못함 |

필수 항목이 FAIL 또는 UNKNOWN이면 자동 주행 요청을 허용하지 않는 구조를 사용한다.

단, 준비 상태 검증이 실제 비상정지 기능을 대체하지는 않는다.

### 5.2. Hardware/Bringup Readiness — C

검증 대상:

- 센서 드라이버 활성화
- LiDAR 데이터 수신
- Odometry 데이터 수신
- 기본 TF 연결
- 모터 구동 인터페이스 확인
- 네트워크와 DDS 통신
- 물리적 장비 장착 및 간섭 상태
- 배터리·전원 상태
- 기존 비상정지 기능 확인

필수 센서 또는 구동 정보가 누락된 상태에서는 PASS로 처리하지 않는다.

### 5.3. Navigation Readiness — D

검증 대상:

- 지도 수신 및 Map Frame
- AMCL 위치 추정 상태
- Nav2 관련 Lifecycle 활성화
- Planner 가용성
- Controller 가용성
- Costmap 및 로봇 Footprint
- 목표 좌표의 유효성
- 현재 로봇 위치와 TF의 최신성
- 경로 생성과 목표 이동 가능 여부

`/amcl_pose`가 수신된다는 사실만으로 위치 추정이 정확하다고 단정하지 않는다.

Nav2 Action 서버가 존재한다는 사실만으로 실제 로봇이 움직일 준비를 완료했다고 간주하지 않는다.

### 5.4. Mission Execution Readiness — A

검증 대상:

- 현재 Mission 상태
- 실행 가능한 TaskStep 존재
- 유효한 RoutePlan
- 활성 Plan Version 일치
- 목표 Waypoint 및 Pose 유효성
- Hardware/Bringup Readiness
- Navigation Readiness
- 주행을 차단해야 할 오류·비상정지 상태

A는 준비 상태가 유효할 때만 미션 실행을 요청한다.

## 6. ROS2 실차 핵심 점검 항목

### 6.1. TF

실제 구성에 따라 다음 연결을 확인한다.

```text
map
 └── odom
      └── base_link
           └── sensor frames
```

일반적인 Nav2 구성에서 확인할 중요한 연결:

- `map → odom`
- `odom → base_link`
- `base_link → LiDAR / Camera`

실제 사용 프레임명은 로봇 구성에서 확인한다.

TF 존재 여부뿐 아니라 갱신 시각·지연·좌표계 연결 상태도 점검한다.

### 6.2. Odometry

- 데이터 수신 여부
- 갱신 주기
- Header Timestamp
- Frame ID
- 실제 로봇 이동과 추정 변화의 일치 여부

Odometry 데이터 수신만으로 위치 추정이 정상이라고 판단하지 않는다.

### 6.3. LiDAR 및 Costmap

- LiDAR Scan 수신
- 센서 Frame과 TF 연결
- 장애물 데이터 반영 여부
- Inflation 및 Robot Footprint 설정
- 목표까지의 통로 확보 여부

좁은 통로에서 Inflation 영역이 겹쳐 이동 불가능한 경우 Costmap과 실제 로봇 크기 및 주행 환경을 검토한다.

안전 여유를 확보하기 위해 설정된 장애물 영역을 무분별하게 줄여 주행을 강행하지 않는다.

### 6.4. AMCL

- 초기 위치 설정
- 위치 추정 결과
- 실제 위치와 지도 좌표 비교
- Scan·Map 정합 상태
- 움직임에 따른 위치 추정 안정성

위치 추정이 불안정하면 주행을 시작하거나 계속하지 않는다.

### 6.5. Nav2 Lifecycle

실제 사용 구성에 따라 다음 컴포넌트의 준비 상태를 확인한다.

- Map Server
- AMCL
- Planner Server
- Controller Server
- BT Navigator
- 관련 Lifecycle Manager

필수 서버가 비활성 상태이거나 정상 응답하지 않으면 자동 주행을 허용하지 않는다.

## 7. 실차 Gate 0~5

각 Gate는 다음 단계로 이동하기 위한 검증 기준이다.

Gate 통과 여부는 실제 시험 기록으로 판단한다.

### Gate 0 — 하드웨어·Bringup

**주요 담당: C**

목표:

- 실제 센서 및 기본 구동환경 확인
- TF·Odometry·통신 정상 여부 검증
- 장비 장착 상태와 안전 조건 확인

**통과 기준**

- 필수 센서 데이터 수신
- 필수 TF 연결 정상
- 기본 Odometry 수신
- 로봇·PC 통신 확인
- 안전 정지 수단 확인
- 장비 준비 절차 문서화

### Gate 1 — 기본 저속 구동

**주요 담당: C·D**

목표:

- 안전한 시험 공간에서 저속 직진·회전·정지 확인
- 구동과 Odometry 반응 검증

**통과 기준**

- 기본 이동 방향 정상
- 회전 방향 정상
- 정지 동작 확인
- 비정상적인 지속 명령 또는 제어 충돌 없음
- 시험 후 로봇이 안전하게 정지한 상태 확인

시험 시 현장 감독과 실제 정지 수단을 확보한다.

### Gate 2 — Nav2 단일 목표 주행

**주요 담당: D / C 지원**

목표:

- AMCL·Nav2 기반 단일 목표 이동
- 목표 도달 결과 및 실패 상태 확인

**통과 기준**

- 유효한 초기 위치와 목표 설정
- Nav2 Planner 경로 생성
- Controller 기반 실제 주행
- 실제 목표 위치 도달 확인
- 결과 상태가 요청과 일치
- TF·AMCL·Lifecycle 관련 치명적 오류 없음

단순히 RViz에 경로가 표시되었다는 이유로 PASS 처리하지 않는다.

### Gate 3 — 복수 지점 및 HOME 복귀

**주요 담당: D·A**

목표:

- HOME 및 작업 지점 A~D 방문
- 복수 목표의 순차 실행
- 마지막 HOME 복귀

**통과 기준**

- 등록된 목표 Pose 사용
- 지점별 목표 이동 및 결과 수신
- 이동 실패가 잘못 완료 처리되지 않음
- HOME 복귀 수행
- 반복 수행 결과 기록

### Gate 4 — 물류 미션 통합

**주요 담당: A·C·D·E**

목표:

- 웹 작업 등록
- 방문 순서 최적화
- 실제 로봇 이동
- 물품 인계 및 완료 처리

**통과 기준**

- Job 및 TaskStep 정상 생성
- 선후 관계 준수
- C의 최적 방문 순서 반환
- A의 실행 승인 및 상태 관리
- D의 실제 주행 수행
- E의 인계 완료 요청 처리
- 완료 작업 중복 실행 없음
- 모든 필수 작업 완료 후 HOME 복귀 및 최종 인계

### Gate 5 — 기본 동적 재계획 및 최종 시연

**주요 담당: 전체**

목표:

- 기존 미션 실행 중 신규 주문 접수
- 남은 작업 순서 재계산
- 현재 작업 보호 및 새로운 계획 적용

**통과 기준**

- 신규 주문 정상 등록
- 완료된 작업 보존
- 진행 중인 작업 보호
- C의 재계획 계산 수행
- 기준 Plan Version 반환
- A의 최신 계획 검사
- 현재 작업 완료 후 새 계획 적용
- D의 변경 목표 주행
- E의 계획 변경 이력 표시
- 최종 미션 완료 및 HOME 복귀

Gate 5의 기본 동적 재계획은 **P0 필수 기능**이다.

복잡한 실패 복구 및 고급 예외 처리는 P1에서 고도화한다.

## 8. 실차 운영 안전 기준

### 8.1. 주행 전

- 주변 인원 및 이동 장애물 확인
- 실험 공간 확보
- 실제 비상정지 수단 확인
- 적절한 저속 시험 조건 확인
- 목표 및 지도 유효성 확인
- Readiness PASS 확인

### 8.2. 주행 중

- 위치 추정 및 TF 상태 감시
- 주행 실패 및 오류 감시
- 로봇의 실제 이동 상태 관찰
- 통신 상태 감시
- 위험 상황에서 기존 검증된 안전 정지 수단 사용

네트워크 단절 시 원격 정지 명령이 전달된다고 보장하지 않는다.

따라서 통신 단절 상황에서의 실제 구동 차단 및 정지 동작은 별도로 검증해야 한다.

### 8.3. 주행 실패 후

- 즉시 자동 재시도하지 않는다.
- 실제 로봇 상태와 Nav2 결과를 확인한다.
- 오류 원인 및 재시도 가능 여부를 판단한다.
- 필요 시 위치 추정과 센서 상태를 다시 검증한다.
- 명시적 복구 절차를 거친 후 재개한다.

E-Stop이 걸린 경우 기존 하드웨어의 복구 절차와 Mission Manager의 실행 상태를 모두 확인한다.

## 9. 실험 데이터 및 기록

### 9.1. 필수 메타데이터

| 항목 | 의미 |
|---|---|
| `experiment_id` | 실험 식별자 |
| `scenario_id` | 시험 환경 |
| `run_mode` | MOCK / SIM / REAL |
| `map_version` | 지도 버전 |
| `config_version` | 설정 버전 |
| `planner_id` | 전역 플래너 |
| `controller_id` | 로컬 제어기 |
| `planned_distance` | 계획 경로 거리 |
| `actual_distance` | 실제 주행 거리 |
| `planning_time` | 계산 시간 |
| `execution_time` | 실제 주행 시간 |
| `goal_success` | 목표 도달 결과 |
| `mission_success` | 미션 완료 결과 |
| `failure_reason` | 실패 원인 |

### 9.2. 계획 경로와 실제 주행 구분

**계획 경로 거리**

Nav2 `ComputePathToPose`로 얻은 `nav_msgs/Path`를 이용해 계산한다.

**실제 주행 거리**

실제 로봇의 Odometry 또는 검증한 위치 데이터를 기반으로 측정한다.

두 값은 동일한 지표가 아니며, 실험 결과에서도 구분해 표시한다.

실주행 데이터의 측정 오차와 위치 추정 한계를 기록한다.

### 9.3. 실험 환경 비교

- 동일한 지도
- 동일한 목표 Pose
- 동일한 장애물 조건
- 동일한 안전 제한
- 비교 대상 외 설정 통제
- 설정 버전 기록
- 반복 시험
- 성공·실패 결과 모두 기록

실차 시험은 기본 기능 검증 후 조건별 5회 이상을 기준으로 하고, 핵심 실험은 가능하면 10회 반복한다.

시험 미실시 항목에는 측정값을 임의로 작성하지 않는다.

## 10. 기존 프로젝트에서 확인된 주요 위험 사례

이전 SMART-VISION-AMR 실차 개발 경험에서 다음과 같은 문제가 관찰되었다.

- `base_link → odom` 관련 TF timeout
- AMCL 위치 추정과 Scan·Map의 불일치
- Nav2 Controller Server 비활성 상태
- 경로는 생성되었지만 실제 로봇이 이동하지 않는 현상
- E-Stop 해제 후 별도 재개 절차가 필요한 상태

이 사례들은 현재 SMART-LOGISTICS AMR의 오류가 이미 발생했다는 뜻이 아니다.

기존 경험을 바탕으로 초기 실차 검증에서 우선 확인할 위험 항목으로 활용한다.

**핵심 판단 기준**

경로가 존재하는 것과 실제 주행이 가능한 것은 별개다.

TF, 위치 추정, Lifecycle, Controller 및 구동 경로까지 확인한 후 주행 가능 여부를 판단한다.

## 12. Gate별 검증 결과 기록

각 Gate의 결과는 다음 형식으로 기록한다.

| 필드 | 기록 내용 |
|---|---|
| Gate ID | 0~5 |
| 시험 일시 | 실제 시험 시각 |
| 담당자 | 시험 및 검증 담당 |
| 실행 환경 | MOCK / SIM / REAL |
| 지도·설정 버전 | 사용한 환경 |
| 검증 항목 | 확인한 기능 |
| 결과 | PASS / FAIL / UNKNOWN |
| 증빙 | 로그·Rosbag·영상·측정 결과 |
| 실패 사유 | 원인 또는 미확인 사항 |
| 후속 조치 | 재시험 또는 수정 필요 사항 |

증빙이 없는 시험은 PASS로 기록하지 않는다.

실차 장비와 관련된 주요 설정 변경은 C·D가 공유하고 A가 통합 기록을 관리한다.
