# PRD — SMART-LOGISTICS AMR

> **문서 상태:** 최종 기획 제안서 기반 요구사항 요약  
> **기준 문서:** `docs/reference/ORIGINAL_PROPOSAL.md`  
> **기준 개정일:** 2026-11-17  
> **개발환경 변경:** 팀 합의에 따라 Ubuntu 24.04 / ROS2 Jazzy 적용  
> **개발 단계:** Phase 1 — 팀원별 담당 기능 개발

본 문서는 SMART-LOGISTICS AMR의 핵심 요구사항, 구현 우선순위, 팀원별 책임과 검증 기준을 요약한 Product Requirements Document(PRD)이다.

세부 기술 설명과 연구 방법은 `ORIGINAL_PROPOSAL.md`를 따른다. 단, 최종 기획서 작성 이후 팀에서 합의한 개발환경 변경은 `docs/DECISIONS.md`에 기록하여 적용한다.

본 문서에 없는 기능이나 세부 구현 사항은 임의로 확정하지 않는다.

## 1. 프로젝트 개요

### 1.1. 기본 정보

| 항목 | 내용 |
|---|---|
| 프로젝트명 | MOVEIT — 교통약자 이동지원을 위한 지능형 수하물 운반 로봇 시스템 |
| 저장소 | SMART-LOGISTICS-AMR |
| 개발 인원 | 5명 |
| 개발 기간 | 2026년 11월 ~ 2027년 1월 |
| 최종 발표 | 2027-01-15 |
| 로봇 | TurtleBot3 Waffle Pi 1대 |
| 운영체제 | Ubuntu 24.04 LTS |
| ROS | ROS2 Jazzy Jalisco |
| Python | 3.12 / rclpy |
| 자율주행 | Nav2, AMCL |
| 시뮬레이터 | Gazebo Harmonic |

개발 PC의 Ubuntu 24.04 / ROS2 Jazzy 환경은 기본 설치 및 동작 검증을 완료했다. 실제 TurtleBot3의 운영체제, 드라이버, 펌웨어 및 센서 호환성은 별도 검증 대상이다.

### 1.2. 프로젝트 목표

이동지원이 필요한 승객은 직원의 도움으로 이동하고, 지정 거점에 맡긴 소형 수하물은 공유 로봇이 운반한다. 담당자는 주문 등록과 수거·전달 인계를 확인한다. 서비스 가설 및 운영 한계는 [MOVEIT 공항 기획](MOVEIT_AIRPORT.md)을 따른다.

여러 물류 작업을 등록하고, 수거·전달의 선후 관계와 Nav2 계획 경로 기반 이동 비용을 고려하여 효율적인 방문 순서를 계산한다.

로봇은 계산된 순서에 따라 작업 지점을 방문하고, 작업자가 물품 인계를 완료하면 다음 단계로 이동한다.

신규 주문이 발생하면 이미 완료된 작업과 진행 중인 작업을 보호하면서 남은 방문 순서를 재계산한다.

최종적으로 알고리즘 비교 실험과 실제 주행 데이터를 통해 시스템의 효율성과 안정성을 검증한다.

### 1.3. 최소 성공 조건

- 실제 TurtleBot3에서 복수 물류 업무 수행
- 수거·전달 선후 관계 준수
- 웹 기반 물품 인계 확인
- 완료된 작업의 중복 실행 방지
- 기본 동적 재계획 정상 수행
- 모든 작업 완료 후 HOME 복귀
- HOME 복귀 후 미션 종료. HOME에 하역 TaskStep이 있으면 사람의 인계 확인까지 수행
- 알고리즘 비교 및 기술 선정 근거 확보

시뮬레이션 성공만으로 실차 기능 완료를 주장하지 않는다.

## 2. 물류 시연 시나리오

### 2.1. 물류 지점

| 환경 | HOME | 수거 접수 거점 | 전달 탑승구 역할 | 총계 |
|---|---|---|---|---|
| 가상 공항 SIM | HOME | S1~S4 | G1~G8 | 13 |
| 강의실 REAL | HOME | S1·S2 | G1·G2 | 5 |

### 2.2. 기본 업무

공항 SIM은 초기 주문 S1→G5, S3→G1, S2→G6, S4→G8을 등록하고 첫 전달 주행 중 S2→G7을 추가한다. 강의실 REAL은 S1→G2, S1→G1로 시작하고 전달 주행 중 S2→G1을 추가한다. 시험 주문과 좌표는 환경별 경로 계산 결과를 확인한 뒤 확정한다.

물품 적재 및 하역은 작업자가 직접 수행한다.

로봇은 물품 인계 완료를 자동 판정하지 않으며, 웹을 통한 작업자 확인을 사용한다.

### 2.3. 작업 모델

- `Job`: 물류 업무 단위
- `TaskStep`: 수거·전달 등 개별 실행 단계
- `Waypoint`: 실제 로봇이 방문하는 물리적 지점
- `Mission`: 전체 작업 실행 상태
- `RoutePlan`: 방문 순서와 예상 이동 비용
- `RobotStatus`: 실제 로봇의 주행 및 연결 상태
- `ExperimentResult`: 실험 조건 및 측정 결과

`Job`, `TaskStep`, `Waypoint`의 ID는 구분한다.

실제 위치 도착과 물품 인계 완료를 동일한 이벤트로 취급하지 않는다.

### 2.4. 미션 실행 흐름

1. 웹에서 작업 등록
2. Mission Manager에서 작업 유효성 검사
3. Route Optimizer에 방문 순서 계산 요청
4. Nav2 계획 경로 비용을 이용한 순서 결정
5. 실제 로봇의 목표 지점 이동
6. 목표 도착 확인
7. 물품 인계 대기
8. 작업자 인계 완료 확인
9. 해당 TaskStep 완료 처리
10. 남은 작업 실행
11. HOME 복귀
12. 필요 시 HOME 최종 하역 확인
13. 전체 미션 완료 처리

## 3. 최종 팀원 역할

| 담당 | 이름 | 핵심 책임 |
|---|---|---|
| A | 윤현수 | Mission Manager, 상태 머신, 재계획 적용 정책, 시스템 통합 |
| B | 정지호 | A*·Dijkstra 전역 경로 탐색 비교 및 최적화 |
| C | 이현수 | 방문 순서 최적화, 동적 재계획 계산, 하드웨어·Bringup 전담 |
| D | 홍근태 | Nav2·AMCL, DWB·RPP, 자율주행 및 도착 정밀 정렬 |
| E | 강연주 | FastAPI, 웹 대시보드, SQLite, 데이터 시각화 |

### 3.1. 책임 경계

**A — 시스템 통합**

- 미션 및 작업 상태 관리
- 최적화 요청 및 결과 검증
- 재계획 적용 시점 결정
- 계획 버전 관리
- 실제 주행 실행 흐름 통제
- 통합 및 완료 판정

**B — 전역 경로 탐색**

- A*·Dijkstra 비교
- 전역 플래너 선정
- 계산 시간·경로 길이·성공률 검증
- C·D와 플래너 설정 및 경로 계산 기준 공유

**C — 물류 최적화·하드웨어**

- Nav2 계획 경로 기반 이동 비용표
- FIFO·Greedy·완전탐색 비교
- 작업 선후 관계를 고려한 방문 순서 계산
- 신규 주문 재계획 계산
- TurtleBot3 하드웨어 점검 및 장비 구성
- 센서·드라이버·TF·ROS2 Bringup 환경 관리

**D — 자율주행·로컬 제어**

- Nav2·AMCL 및 주행 관련 설정
- 목표 이동 및 피드백 제공
- DWB·RPP 비교
- 실제 주행 안정화 및 오류 대응
- 필요 시 ArUco 도착 정밀 정렬

**E — 웹 관제·데이터**

- 주문 등록 및 인계 완료 요청
- 현재 작업·미션 상태 표시
- 계획 경로 및 로봇 위치 시각화
- 실험 결과 저장 및 비교
- SQLite 및 웹 API 관리

C의 물류 최적화와 하드웨어·Bringup은 같은 담당자가 개발하되 별도 소프트웨어 패키지로 관리한다.

## 5. 핵심 알고리즘 연구

| 연구 | 담당 | 비교 대상 | 주요 검증 지표 |
|---|---|---|---|
| 전역 경로 탐색 | B | A* vs Dijkstra | 계산 시간, 경로 길이, 생성 성공률 |
| 방문 순서 최적화 | C | FIFO vs Greedy vs 완전탐색 | 이동 비용, 실제 거리·시간, 계산 시간, 선후 관계 준수 |
| 로컬 주행 제어 | D | DWB vs RPP | 추종 오차, 도달 성공률, 시간, 안정성 |

### 5.1. 계획 경로와 실제 주행 데이터 구분

Nav2 `ComputePathToPose`로 얻은 경로는 실제 주행 궤적이 아닌 계획 경로다.

- `planned_distance`: Nav2 계획 경로 길이
- `actual_distance`: 실제 로봇 주행 거리
- `planning_time`: 경로 또는 순서 계산 시간
- `execution_time`: 실제 주행 시간

계획 경로 비용은 방문 순서 계산에 사용하고, 실제 주행 데이터는 알고리즘 효과 및 타당성 검증에 사용한다.

비교 실험 시 지도, 지점 좌표, Costmap, 플래너 및 Controller 설정과 버전을 기록한다.

### 5.2. 계획 경로 비용표

C는 D가 관리하는 Nav2 실행 환경을 통해 `ComputePathToPose` 기반 이동 비용을 계산한다.

B가 선정한 전역 플래너 설정을 적용하고, 고정 지점 간 경로 계산에서는 명시적인 출발·목표 자세를 사용한다.

방향에 따른 이동 비용 차이를 고려하여 출발·도착 순서별 비용을 각각 관리한다.

지도의 변경이나 플래너 설정 변경이 발생하면 기존 비용표의 유효성을 재검증한다.

### 5.3. 초기 최적화 범위

강의실은 HOME을 제외한 4개 지점에서 소규모 주문으로 통합한다. 공항 SIM은 13개 지점에서 주문 5건부터 비교한다. 동일 조건에서 FIFO와 최적화의 총 비용·공차 비용을 기록한다.

단순 방문 순서 후보는 최대 24개이며, B 지점 수거 후 C 지점 전달 선후 관계만 추가하면 12개 순서가 유효하다.

완전탐색은 초기 소규모 시나리오의 최적해 검증 기준으로 사용한다.

재방문과 동일 지점의 다중 TaskStep 처리는 후속 확장 가능성을 고려하되 Priority P0 구현 범위를 불필요하게 확대하지 않는다.

## 6. 동적 재계획 요구사항

### 6.1. 기본 동작

1. E에서 신규 주문 접수
2. A가 현재 미션·작업 상태 확인
3. A가 C에 재계획 계산 요청
4. C가 선후 관계와 남은 작업을 이용해 새 방문 순서 계산
5. C가 기준 계획 버전과 계산 결과 반환
6. A가 현재 상태 및 버전 검증
7. A가 진행 중인 작업 완료 후 새 계획 적용
8. D가 새로운 목표 순서에 따라 이동
9. E가 변경된 계획과 진행 상태 표시

### 6.2. 핵심 제약

- 완료된 작업의 상태 보존
- 현재 진행 중인 작업 보호
- 중복 작업 실행 방지
- 선후 관계 준수
- 기준 계획 버전 검증
- 오래된 재계획 결과의 적용 방지
- 현재 주행 목표를 임의로 반복 취소하지 않음
- 재계획 실패 시 미션 상태의 일관성 유지

**계산 주체는 C, 적용·실행 승인 주체는 A이다.**

## 7. 환경 및 구현 제약

### 7.1. 개발환경

**공식 개발 기준**

- Ubuntu 24.04 LTS
- ROS2 Jazzy Jalisco
- Python 3.12 / rclpy
- Nav2 / AMCL
- Gazebo Harmonic / ros_gz
- TurtleBot3 Waffle Pi
- FastAPI / SQLite
- HTML / CSS / JavaScript
- LiDAR 및 필요 시 카메라

기존 Ubuntu 22.04 / ROS2 Humble은 이전 개발환경이며, 본 프로젝트의 신규 구현 기준으로 사용하지 않는다.

**개발환경 아키텍처**

- 초기 개발 VM: Ubuntu 24.04 ARM64(aarch64), UTM 기반
- 실제 TurtleBot3 컴퓨팅 보드: 장비 확인 후 지원 OS·아키텍처·ROS2 버전 검증
- 팀원 개발 PC: 공통 ROS2 Jazzy 기준 준수
- ROS2 통신: DDS 및 네트워크 설정을 실제 환경에서 확인

실제 설치 버전, 센서 모델, ROS2 Topic과 Frame 명칭은 확인 후 기록한다.

개발 VM의 정상 동작을 실차의 호환성 검증 완료로 간주하지 않는다.

### 7.2. 시뮬레이션 환경 제약

Gazebo Harmonic을 기본 시뮬레이터로 사용한다.

초기 UTM ARM64 환경에서 다음을 확인했다.

- ROS2 Jazzy 및 Python rclpy 정상 동작
- ROS2 Talker / Listener 통신 성공
- colcon 기반 Python 패키지 생성·빌드·실행 성공
- Gazebo Harmonic 기본 월드 실행 성공
- RViz2 GUI 실행 성공

다만 UTM에서 VirGL GPU 가속 적용 시 Gazebo·RViz2 그래픽 문제가 발생했다.

CPU 기반 `llvmpipe` 렌더링에서는 기본 GUI 실행이 가능했지만, Gazebo 구동 중 CPU 사용량과 발열이 크게 증가했다.

따라서 복잡한 시뮬레이션의 장시간 실행 가능 여부는 추가 검증하며, 필요 시 Headless 실행이나 별도 Ubuntu 개발 장비를 활용한다.

이는 초기 개발 VM에서 확인된 제약이며, 다른 개발환경에 동일하게 적용되는 것은 아니다.

### 7.3. 구현 제외 범위

## 8. Sim-to-Real 검증

### 8.1. 실행 환경

| 환경 | 목적 |
|---|---|
| MOCK | 상태 머신과 모듈 계약 검증 |
| SIM | Gazebo Harmonic 기반 자율주행·통합 검증 |
| REAL | 실제 TurtleBot3 주행 검증 |

`use_sim_time`은 시간 기준 설정이며, 실행 환경 자체를 격리하지 않는다.

### 8.2. 검증 책임

- **C:** 센서·드라이버·TF·통신·Bringup 준비 상태
- **D:** AMCL·Nav2 Lifecycle·Planner·Controller 및 주행 준비 상태
- **A:** 필수 준비 상태 확인과 전체 미션 실행 승인
- **B:** 전역 플래너의 실차 검증
- **E:** 상태·실험 결과 기록과 관제

### 8.3. 실차 검증 Gate

| Gate | 목표 | 주요 담당 |
|---|---|---|
| 0 | 하드웨어·센서·통신·TF 확인 | C |
| 1 | 저속 수동 주행 및 정지 | C·D |
| 2 | Nav2 단일 목표 이동 | D, C 지원 |
| 3 | 다중 지점 이동 및 HOME 복귀 | D·A |
| 4 | 물류 업무와 실제 주행 통합 | A·C·D·E |
| 5 | 신규 주문 동적 재계획 및 최종 시연 | 전체 |

필수 준비 항목은 PASS / FAIL / UNKNOWN으로 구분하고, FAIL 또는 UNKNOWN 상태에서 자동 주행을 허용하지 않는 구조를 검토한다.

실제 안전 정지 및 복구 절차는 로봇 하드웨어의 지원 여부를 확인하고 검증한다.

### 8.4. TurtleBot3 Jazzy 전환 검증

실제 TurtleBot3의 Jazzy 전환은 개발 VM 구성과 별도 작업으로 관리한다.

다음 항목을 확인한다.

1. Raspberry Pi 및 기타 제어 보드의 정확한 모델
2. Raspberry Pi에 적용할 운영체제와 CPU 아키텍처
3. TurtleBot3 관련 ROS2 Jazzy 패키지·드라이버 지원 여부
4. OpenCR 펌웨어 및 모터 제어 호환성
5. LiDAR·카메라 등 센서 드라이버 호환성
6. 개발 PC와 로봇 간 DDS 통신 및 네트워크 설정
7. TF, Odometry, 센서 토픽 및 기본 주행 검증
8. Nav2·AMCL 실차 주행 검증

실차 OS 재설치나 펌웨어 변경은 백업 및 복구 가능성을 확인한 뒤 담당자 간 합의하여 수행한다.
