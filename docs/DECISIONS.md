# 기술 의사결정 기록 — SMART-LOGISTICS AMR

> **문서 상태:** 기술 의사결정 기록 v1.0  
> **최종 승인권자:** A — 윤현수 (팀장)  
> **기획 기준:** 2026.11.17 최종 기획 제안서  
> **아키텍처:** 초기 아키텍처 v1.0 승인  
> **최종 발표:** 2027-01-15  
> **현행 개발 기준:** Ubuntu 24.04 LTS / ROS2 Jazzy / Gazebo Harmonic

본 문서는 SMART-LOGISTICS AMR 프로젝트에서 승인한 설계 결정, 미확정 기술 사항 및 변경 이력을 관리한다.

기술적 제안과 실제 승인된 결정을 구분하며, Codex를 포함한 모든 개발 도구는 본 문서의 결정 상태를 기준으로 작업한다.

본 문서에서 **승인**은 설계 적용의 승인이지, 기능 구현이나 실차 검증 완료를 의미하지 않는다.

---

## 1. 의사결정 관리 원칙

### 1.1. 결정 상태

| 상태 | 의미 |
|---|---|
| **APPROVED** | 팀장이 승인한 설계·정책 |
| **PENDING** | 세부 기술 또는 구현 방식 결정 대기 |
| **VERIFY** | 설계 방향은 있으나 실제 환경에서 검증 필요 |
| **SUPERSEDED** | 이후 결정으로 대체된 과거 결정 |

### 1.2. 승인 및 변경 원칙

- 최종 기술 설계 승인권자는 A 담당 윤현수다.
- 각 담당자는 자신의 기술 영역에서 설계·개선안을 제안할 수 있다.
- 공통 아키텍처와 인터페이스 변경은 영향 범위 검토 후 A의 승인을 받아 적용한다.
- 승인된 사항은 Codex가 임의로 재설계하지 않는다.
- 실험 결과가 기존 결정을 변경할 충분한 근거가 되면 변경안을 제시한다.
- 승인된 변경은 관련 문서에 함께 반영한다.
- 실차 측정값이나 검증 결과를 임의로 작성하지 않는다.

### 1.3. 문서 우선순위

1. `docs/reference/ORIGINAL_PROPOSAL.md` — 기술·역할 기준. 활용 목적·시연 변경은 ADR-016 및 `docs/MOVEIT_AIRPORT.md` 적용
2. `AGENTS.md` — 프로젝트 공통 개발 규칙
3. `docs/PRD.md` — 핵심 요구사항 및 우선순위
4. `docs/ARCHITECTURE.md` — 승인된 아키텍처
5. `docs/INTERFACES.md` — 공통 인터페이스 설계 기준
6. `docs/SIM_TO_REAL.md` — 실차 검증 기준
7. `docs/DECISIONS.md` — 개별 기술 결정 및 변경 기록

기획 요구사항과 기술 설계가 충돌할 경우 기획서를 기준으로 검토한다. 단, 기획서 이후 승인된 개발환경 변경은 해당 ADR의 결정에 따른다.

본 문서에서 승인된 기술적 결정은 관련 세부 설계 문서에도 반영한다. 서로 다른 문서에 충돌하는 내용이 존재하면 임의로 선택하지 않고 수정 대상과 원인을 보고한다.

## 2. 승인된 기술 결정

### ADR-001 — 프로젝트 아키텍처 v1.0 승인

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A

**결정**

SMART-LOGISTICS AMR의 초기 시스템 아키텍처 v1.0을 프로젝트의 개발 기준으로 사용한다.

기본 구조는 단일 Git 저장소(Monorepo)이며, ROS2 패키지와 웹 서버를 담당 영역별로 구분한다.

**결정 이유**

- 5명 병렬 개발 및 통합
- 모듈별 책임 명확화
- 공통 메시지·설정 변경 관리
- 실제 로봇과 Mock 환경의 단계별 통합
- 불필요한 패키지 및 추상화 방지

**관련 문서**

- `docs/ARCHITECTURE.md`
- `docs/PRD.md`

실제 패키지 생성·빌드 성공 여부는 별도로 검증한다.

### ADR-002 — 최종 5인 역할 분담

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A

| 담당 | 이름 | 책임 |
|---|---|---|
| A | 윤현수 | Mission Manager, 상태 머신, 재계획 적용 정책, 통합 |
| B | 정지호 | A*·Dijkstra 전역 경로 탐색 |
| C | 이현수 | 방문 순서 최적화, 동적 재계획 계산, 하드웨어·Bringup |
| D | 홍근태 | Nav2·AMCL, DWB·RPP, 자율주행·정밀 정렬 |
| E | 강연주 | FastAPI, 웹 관제, SQLite, 데이터 시각화 |

**결정**

- B는 전역 경로 탐색 연구를 담당한다.
- C는 물류 최적화와 하드웨어·Bringup을 모두 담당한다.
- D는 Nav2 기반 자율주행과 로컬 제어를 담당한다.
- A는 시스템 미션 상태 및 재계획 적용을 담당한다.
- E는 작업 입력과 관제·데이터 기능을 담당한다.

담당자 역할을 변경할 경우 본 결정과 패키지 소유권, 인터페이스 문서를 함께 수정한다.

### ADR-003 — 초기 패키지 구조 및 소유권

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A

| 패키지 또는 영역 | 담당 |
|---|---|
| `logistics_msgs` | A 관리, 팀 공통 |
| `mission_manager` | A |
| 전역 플래너 연구 코드·설정 | B |
| `route_optimizer` | C |
| `amr_bringup` | C |
| `amr_navigation` | D |
| `web_control` | E |

**결정**

5개 기본 ROS2 패키지와 별도 웹 영역을 초기 개발 구조로 사용한다.

C의 `route_optimizer`와 `amr_bringup`은 같은 담당자가 개발하더라도 별도 패키지로 구분한다.

B의 전역 경로 탐색 연구는 우선 Nav2 기본 플래너 및 비교 도구를 활용하며, 독립 ROS2 패키지 추가는 필수로 요구하지 않는다.

**유의 사항**

패키지 구조와 담당 소유권은 승인되었지만 내부 노드명, 메시지명, Service·Action 이름과 세부 구현은 아직 확정되지 않았다.

### ADR-004 — Mission Manager의 상태 관리 권한

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A

**결정**

A의 Mission Manager를 미션 및 작업 실행 상태의 단일 관리 주체로 한다.

- Job·TaskStep·Mission 상태 관리
- 물품 인계 완료 판정
- 방문 순서 계산 요청
- 계산 결과 검증 및 적용
- Nav2 주행 요청
- 미션 종료 판정

E는 웹을 통해 인계 완료를 요청하지만 실행 상태를 독자적으로 확정하지 않는다.

C는 최적 방문 순서를 계산하지만 Mission 상태를 직접 변경하지 않는다.

D는 주행 결과를 반환하지만 물품 인계 완료를 판정하지 않는다.

### ADR-005 — Job·TaskStep·Waypoint 분리

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A

**결정**

- `Job`: 물류 업무
- `TaskStep`: 실제 수거·전달 단계
- `Waypoint`: 지도상의 물리적 위치

각 개념의 ID와 상태를 구분한다.

목표 지점 도착과 실제 물품 인계 완료는 서로 다른 이벤트로 처리한다.

수거 완료 이전에 해당 물품의 전달 단계를 실행할 수 없다.

완료된 작업을 중복 실행하지 않는다.

### ADR-006 — 계획 경로 기반 방문 순서 최적화

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A

**결정**

방문 순서 최적화에는 단순 직선거리 대신 Nav2 `ComputePathToPose`에서 얻은 계획 경로의 길이를 이동 비용으로 사용한다.

- 계획 경로 비용 계산 담당: C
- 전역 플래너 연구·선정: B
- Nav2 Planner 실행·설정 관리: D

계획 경로와 실제 주행 궤적을 구분한다.

비용표는 지도, 플래너 설정 및 지점 좌표 등의 변경 시 유효성을 재검증한다.

**실험 대상**

- FIFO
- Greedy
- 완전탐색

최종 최적화 알고리즘은 반복 실험 결과를 기준으로 선정한다.

따라서 세 후보 중 특정 알고리즘의 최종 채택 여부는 아직 결정되지 않았다.

### ADR-007 — 기본 동적 재계획 Priority P0 필수

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A

**결정**

신규 주문 발생 시 기본 동적 재계획 기능을 Priority P0 필수 구현에 포함한다.

**계산 책임: C**

- 신규 주문 반영
- 남은 작업 순서 재계산
- 선후 관계 유지
- 계획 기준 버전 반환

**적용 책임: A**

- 현재 작업 상태 검증
- 계산 결과 최신성 확인
- 진행 중인 작업 보호
- 새로운 계획 적용 시점 결정

**기본 정책**

현재 진행 중인 작업을 완료한 뒤 다음 작업부터 새 계획을 적용한다.

오래된 재계획 결과가 최신 계획을 덮어쓰지 않도록 한다.

복잡한 실패 복구와 고급 충돌 처리는 Priority P1에서 구현한다.

### ADR-008 — 전역 경로 탐색 및 로컬 제어 비교

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A

**연구 1 — B**

- A* vs Dijkstra
- 경로 계산 시간·길이·성공률 비교
- 최종 전역 플래너 선정

**연구 3 — D**

- DWB vs Regulated Pure Pursuit
- 주행 시간·경로 추종 오차·도달률 비교
- 최종 Controller 선정

**결정**

세부 알고리즘의 최종 채택 결과는 실험을 수행한 뒤 결정한다.

A* 또는 DWB 등 특정 기술이 이미 우수하다고 가정하지 않는다.

DWB·RPP 비교는 Priority P1 핵심 연구로 관리한다.

### ADR-009 — 하드웨어·Bringup과 Nav2 책임 분리

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A

**C — 하드웨어 및 Bringup**

- TurtleBot3 물리적 장비
- 센서 및 드라이버
- TF·Odometry 기본 환경
- 로봇·PC 통신
- 기본 Launch 및 실행 매뉴얼
- 바스켓·카메라 설치 및 장비 구성

**D — 자율주행**

- AMCL
- Nav2 Lifecycle
- Planner·Controller·Costmap
- 목표 주행
- 주행 실패·복구
- 도착 정밀 정렬

두 담당자는 실차 환경 변경과 오류 분석에 필요한 정보를 공유한다.

### ADR-010 — MOCK / SIM / REAL 검증 분리

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A

**결정**

- MOCK: 상태 머신과 공통 인터페이스 검증
- SIM: Gazebo·Nav2 시뮬레이션 검증
- REAL: 실제 TurtleBot3 검증

시뮬레이션 성공을 실차 성공으로 간주하지 않는다.

`use_sim_time`은 시간 기준 설정이며 DDS·네트워크 격리의 대체 수단이 아니다.

실차 검증은 Gate 0~5를 기준으로 수행한다.

**유의 사항**

검증 절차가 승인되었다는 사실은 Gate 통과를 의미하지 않는다.

현재 각 Gate의 실제 PASS 여부는 시험 증빙으로 별도 기록해야 한다.

### ADR-011 — 안전 및 실행 승인 정책

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A

**결정**

실제 로봇의 자동 미션 실행 전 다음 준비 상태를 확인한다.

- C: Hardware/Bringup Readiness
- D: Navigation Readiness
- A: Mission Execution Readiness

필수 준비 상태가 FAIL 또는 UNKNOWN이면 자동 미션 실행을 허용하지 않는다.

주행 중에도 센서·위치 추정·안전 상태를 감시한다.

안전 정지와 복구 기능은 실제 하드웨어 지원 여부를 확인하고 시험한다.

### ADR-012 — 실험 데이터 및 성능 검증

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A

**결정**

- 계획 경로 길이와 실제 주행 거리를 구분한다.
- 계산 시간과 실제 주행 시간을 구분한다.
- 동일한 조건에서 알고리즘을 비교한다.
- 설정 버전, 지도 버전, 실행환경을 기록한다.
- 성공 및 실패 데이터를 모두 기록한다.
- 실험을 하지 않은 항목에 임의의 수치를 작성하지 않는다.
- ExperimentResult는 기본적으로 JSON·CSV·SQLite에서 관리한다.

실차 실험은 초기 검증 이후 조건별 5회 이상을 기본으로 하고, 주요 최종 실험은 가능하면 10회 반복한다.

### ADR-013 — 기능 우선순위

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A

**Priority P0**

- 실차 Bringup
- Nav2 기본 주행
- 물류 작업 상태 머신
- 계획 경로 비용표
- 방문 순서 최적화
- 물품 인계 및 HOME 복귀
- 웹 관제
- A*·Dijkstra 비교
- FIFO·Greedy·완전탐색 비교
- 기본 동적 재계획

**Priority P1**

- DWB·RPP 비교
- 고급 재계획 예외 처리
- 복구 로직 고도화
- 고급 시각화
- ArUco 정밀 정렬

**Priority P2**

- 자연어·음성 입력
- 추가 최적화
- 실험 자동화 등 선택 기능

Priority P1·Priority P2 기능 때문에 Priority P0 전체 미션 개발을 지연시키지 않는다.

**2026-11-18 표기 규칙.** Priority P0는 필수 기능, Priority P1은 추가·고도화 기능, Priority P2는 선택 기능이다. 개발 단계는 다음과 같이 구분한다. Phase 0 완료는 위 필수 기능 전체의 완료를 뜻하지 않는다.

| 개발 단계 | 작업 범위 |
|---|---|
| Phase 0 | 공통 ROS2 기반 구축 |
| Phase 1 | 팀원별 담당 기능 개발 |
| Phase 2 | 모듈 통합 |
| Phase 3 | 시스템 검증 및 최종 시연 |

### ADR-014 — 개발 기준 Ubuntu 24.04 / ROS2 Jazzy 전환

- **상태:** APPROVED
- **기준일:** 2026-11-17
- **승인권자:** A (팀 합의 반영)

**결정**

- 공식 개발 운영체제는 Ubuntu 24.04 LTS로 한다.
- ROS2 배포판은 Humble에서 Jazzy Jalisco로 전환한다.
- Nav2는 Jazzy 호환 버전을 사용하고, 시뮬레이터는 Gazebo Harmonic을 기준으로 한다.
- 기존 Humble 코드·설정을 재사용할 때 Jazzy API, 패키지 의존성 및 설정 호환성을 확인한다.
- 승인된 아키텍처 v1.0, 팀 역할, Mission Manager의 상태 관리 권한 및 동적 재계획 정책은 변경하지 않는다.

**확인된 개발환경**

- Mac M2 / UTM / Ubuntu 24.04 ARM64에서 ROS2 Jazzy, rclpy 및 colcon 기본 실행을 확인했다.
- Gazebo Harmonic 기본 월드 및 RViz2 기본 GUI 실행을 확인했다.
- UTM의 VirGL 그래픽 가속 환경에서는 GUI 문제가 발생해, 현재 검증된 기본 실행환경은 비가속 VirtIO의 llvmpipe 소프트웨어 렌더링이다.
- 위 결과는 기초 개발환경의 확인 사항으로, 본 프로젝트의 로봇 시뮬레이션 전체 주행이나 실제 TurtleBot3의 Jazzy 전환 완료를 의미하지 않는다.

**후속 검증**

- C는 실제 TurtleBot3의 컴퓨팅 보드, OS·아키텍처, ROS2 드라이버 및 OpenCR 펌웨어 호환성을 확인한다.
- D는 Jazzy 환경의 Nav2·AMCL·Planner·Controller를 실차에서 검증한다.
- 실차 OS 재설치나 펌웨어 변경은 기존 환경의 백업·복구 절차를 마련한 뒤 진행한다.

### ADR-015 — 병렬 개발 공통 계약 (2026-11-18, A 승인)

### ADR-016 — MOVEIT 공항 이동지원 적용 및 시연 범위 (2026-11-24, A 승인)

- 기존 저장소와 설계를 유지하고, 이동지원 직원이 승객을 돕는 동안 공유 AMR이 소형 수하물을 운반하는 서비스 시나리오를 적용한다.
- 가상 공항 SIM 13개 지점은 최적화·재계획 연구에, 강의실 REAL 5개 지점은 로봇 주행과 사람의 인계 검증에 사용한다. 기존 샌드박스는 별도 회귀 기준이다.
- 범용 물류 시연의 지점 이름과 주문 예시를 새 시연 정의로 대체한다. 기존 기술·팀 역할·인터페이스·HOME 하역 계약은 계속 따른다.
- 새 하드웨어와 적재용량·탑승 기한은 미확정이다. 공항 현장 운영과 실차 검증 상태는 [시나리오와 증빙](MOVEIT_AIRPORT.md)에 기록한다.

## 7. Codex 적용 원칙

Codex는 작업 시작 시 다음 사항을 확인한다.

1. 해당 작업의 요구사항이 최종 기획서와 일치하는가?
2. 관련 아키텍처 결정이 APPROVED 상태인가?
3. 현재 작업에 PENDING 또는 VERIFY 항목이 포함되어 있는가?
4. 다른 담당자의 모듈이나 공통 인터페이스를 변경하는가?
5. 실제 환경에서 검증되지 않은 사항을 사실로 가정하고 있지 않은가?

승인된 구조를 이유 없이 다시 설계하지 않는다.

미확정 기술은 구현 대안을 비교하고 권고안을 제시한다.

공통 인터페이스와 아키텍처를 변경하려면 변경 이유와 영향 범위를 보고하고 A의 승인을 받는다.

**최종 원칙: 승인된 결정은 개발 기준으로 유지하되, 실험과 실제 환경에서 검증되지 않은 기술 세부사항은 확정된 사실로 취급하지 않는다.**
