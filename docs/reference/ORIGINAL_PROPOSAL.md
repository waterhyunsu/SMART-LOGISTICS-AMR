## 1. 프로젝트 개요

### 1.1. 개발 배경

자율주행 모바일 로봇(AMR)은 물류 환경에서 반복적인 운반 및 이동 작업에 활용된다.

그러나 복수의 물류 요청을 처리하기 위해서는 단순히 목적지까지 이동하는 기능을 넘어 작업 순서, 이동 효율, 작업 완료 상태를 함께 고려해야 한다.

대표적으로 다음과 같은 문제가 발생한다.

- 주문 접수 순서에 따른 불필요한 왕복 이동
- 물품 수거·전달 사이의 선후 관계
- 신규 주문 발생에 따른 작업 계획 변경
- 목적지 도착과 실제 물품 인계 완료의 차이
- 경로 탐색 및 주행 제어 방식에 따른 성능 차이
- 작업 진행 상황과 오류에 대한 통합 관리 필요성

본 프로젝트에서는 이러한 문제를 해결하기 위해 다중 물류 작업 스케줄링, 계획 경로 기반 최적화, 자율주행 및 중앙 미션 관제를 통합한 물류 운반 시스템을 개발한다.

또한 주요 알고리즘을 동일한 조건에서 비교·검증하고, 실제 주행 데이터와 측정 결과를 근거로 최종 기술을 선정한다.

### 1.2. 핵심 개발 목표

1. **다중 물류 작업 최적화:** Nav2 계획 경로에 따른 이동 비용을 기반으로 효율적인 방문 순서 계산
2. **작업 제약 관리:** 수거·전달 선후 관계 및 작업 완료 조건 준수
3. **자율주행 미션 실행:** 여러 작업 지점 방문, 물품 인계 대기, HOME 복귀
4. **동적 재계획:** 신규 주문 발생 시 남은 작업 순서 재계산 및 안전한 시점에 적용
5. **알고리즘 비교·검증:** 전역 경로 탐색, 물류 최적화, 로컬 주행 제어 비교
6. **데이터 기반 기술 선정:** 반복 실험과 실주행 결과를 근거로 알고리즘 채택
7. **통합 웹 관제:** 주문, 위치, 경로, 작업 상태 및 실험 결과 관리

### 1.3. 개발 원칙

**문제 정의 → 후보 기술 선정 → 비교 실험 → 결과 분석 → 기술 결정 → 시스템 적용 → 통합 재검증**

각 알고리즘 담당자가 자신의 연구 영역을 직접 비교하고, 기술 선정 근거를 기록한 뒤 최종 구현까지 책임진다.

다만 실험이 완료될 때까지 모든 개발을 중단하지는 않는다. 기본 구현이나 임시 인터페이스를 이용해 병행 개발하고, 검증 결과가 확정되면 최종 구현으로 교체한다.

특히 시뮬레이션의 성공을 실차 성공으로 간주하지 않으며, 실제 TurtleBot3의 기본 구동과 자율주행 가능 여부를 개발 초기부터 검증한다.

## 2. 개발 환경과 구현 범위

### 2.1. 기술 환경

| 구분 | 적용 기술 |
|---|---|
| 로봇 | TurtleBot3 Waffle Pi |
| 운영체제 | Ubuntu 22.04 |
| ROS | ROS2 Humble |
| 자율주행 | Nav2, AMCL, LiDAR |
| 개발 언어 | Python |
| 영상 처리 | OpenCV, ArUco (선택) |
| 백엔드 | FastAPI |
| 데이터 저장 | SQLite, CSV |
| 실시간 통신 | WebSocket 또는 rosbridge 기반 연동 |
| 개발 장비 | 기존 교육용 로봇 및 PC |
| 시연 환경 | 기존 강의실 |
| 예산 | 추가 50,000원 이내 |

실제 하드웨어, 센서 모델, ROS2 패키지 버전, 드라이버 및 설치 환경은 **C 담당 이현수**가 확인하고 기록한다.

D 담당 홍근태는 C가 구축한 로봇 기본 실행환경을 바탕으로 Nav2·AMCL 및 자율주행 기능을 구성하고 검증한다.

A 담당 윤현수는 공통 개발환경의 변경 사항과 실차 테스트 일정을 관리한다.

### 2.2. 물류 지점 구성

HOME과 작업 지점 4곳을 사용한다.

| 지점 | 역할 |
|---|---|
| HOME | 물품 초기 적재, 최종 하역 및 복귀 |
| A | 초기 물품 전달 |
| B | 물품 수거 |
| C | B에서 수거한 물품 전달 |
| D | HOME으로 회수할 물품 수거 |

**초기 예시 업무**

- `JOB-001`: HOME → A
- `JOB-002`: B → C
- `JOB-003`: D → HOME

모든 지점에는 지도상의 고정 위치와 목표 방향을 등록한다.

실제 지점 배치, 이동 가능 공간, 경로 비용, 도킹 허용 오차는 강의실 환경 검증 후 결정한다.

문서의 `A~E 담당 코드`는 팀원 구분이며, `A~D 지점`은 물류 작업 위치를 의미한다. 두 식별 체계는 별개로 관리한다.

### 2.3. 하드웨어 구현 원칙

**포함**

- 기존 터틀봇 구동 장치 및 센서
- LiDAR 및 필요 시 카메라
- 경량 물품 운반용 바스켓
- 규격 물품 모형
- HOME 및 작업 지점 표식
- ArUco 마커(정밀 정렬 기능 적용 시)
- 공통 ROS2 및 통신 환경

**제외**

- 지점별 IoT 장치
- ESP32·Arduino 기반 시설 제어
- 시설 점검 및 자동 대응
- 자동 집게 또는 로봇팔
- 적재 용량·무게·부피 측정
- 물품 자동 적재·하역
- 다중 로봇 교통 제어

물품 적재 및 하역은 작업자가 수행하며 웹 화면에서 인계 완료를 확인한다.

따라서 프로젝트는 주행 및 작업 계획이 자동화된 **반자동 물류 운반 시스템**으로 정의한다.

물품은 실제 바스켓에 무리 없이 배치할 수 있도록 사전에 규격과 시연 시나리오를 정한다. 적재 용량은 알고리즘의 제약 조건에 포함하지 않는다.

### 2.4. 하드웨어 및 Bringup 책임

하드웨어와 ROS2 기본 구동 환경은 **C 담당 이현수가 전담**한다.

| 구분 | 담당 | 책임 |
|---|---|---|
| 로봇 기본 장비 | C | TurtleBot3 하드웨어 상태 점검 및 구동 환경 확보 |
| 물리적 장비 구성 | C | 바스켓·카메라·LiDAR 간섭 확인, 장착 및 케이블 정리 |
| 센서 및 드라이버 | C | LiDAR·카메라·Odometry·IMU 등 장착 장비 확인 |
| ROS2 Bringup | C | 로봇 기본 실행, Topic, TF 및 통신 환경 |
| Nav2·AMCL | D | 위치 추정, Costmap, Planner·Controller 실행 및 주행 |
| 공통 운영 관리 | A | 실차 사용 일정, 통합 버전, 설정 변경 사항 관리 |

C는 로봇 기본 구동과 센서·통신 환경의 정상 동작을 보장하는 역할이다.

D는 해당 기반 환경에서 실제 자율주행 기능을 구성하고 성능을 검증한다.

C의 Bringup 책임과 D의 Nav2 설정 책임은 분리한다. 두 담당자 간 변경이 필요한 경우 인터페이스와 설정 변경 내용을 공유한다.

## 3. 작업 모델 및 시스템 동작

### 3.1. 작업과 방문 지점 구분

`Job`은 수행해야 할 업무이고, `Waypoint`는 로봇이 방문하는 물리적 위치이다.

예를 들어 `JOB-002: B → C`는 다음 두 작업 단계로 분리된다.

- `JOB-002-PICKUP`: B에서 물품 수거
- `JOB-002-DROPOFF`: C에서 물품 전달

이때 전달 단계는 수거 단계가 완료된 뒤에만 실행할 수 있다.

하나의 방문 지점에서 여러 작업이 발생하면 해당 지점에서 수행할 작업들을 각각 관리한다.

초기 구현에서는 각 작업 지점 A~D를 한 번씩 방문하는 시나리오를 사용한다. 이후 같은 지점에 여러 작업이 발생하거나 재방문이 필요한 경우까지 확장할 수 있다.

### 3.2. 작업 상태

| 상태 | 의미 |
|---|---|
| `PENDING` | 등록된 작업 |
| `READY` | 선행 조건을 만족한 작업 |
| `IN_PROGRESS` | 현재 수행 중인 작업 |
| `WAITING_CONFIRMATION` | 물품 인계 확인 대기 |
| `COMPLETED` | 실제 작업 완료 확인 |
| `FAILED` | 작업 실패 |
| `CANCELLED` | 작업 취소 |

주행 상태와 작업 상태는 별도로 관리한다.

예를 들어 B 지점에 도착했더라도 물품을 수거하지 않았다면 `JOB-002-PICKUP`은 완료되지 않은 상태다.

### 3.3. 기본 업무 흐름

**주문 등록 → 작업 검증 → 방문 순서 최적화 → 자율주행 → 지점 도착 → 물품 인계 → 작업 완료 확인 → 다음 지점 이동 → HOME 복귀**

작업 완료 버튼은 실제 물품 인계가 이루어진 뒤에 누른다.

물품 인계가 확인되지 않은 상태에서는 다음 작업으로 자동 전환하지 않는다.

HOME으로 운반해야 할 물품이 있다면, HOME 도착 후 최종 하역 확인까지 완료되어야 전체 미션을 `COMPLETED`로 처리한다.

### 3.4. 기본 최적화 제약 조건

- 등록된 지점만 사용
- 이동 가능한 경로만 사용
- 수거 이전 해당 물품의 전달 금지
- 완료된 작업의 중복 실행 방지
- 진행 중인 작업 상태 보존
- 마지막 작업 이후 HOME 복귀
- HOME으로 회수한 물품의 최종 하역 확인

적재 용량은 고려하지 않는다.

### 3.5. 신규 주문 발생 시 재계획

신규 주문이 발생하면 현재 작업 상태와 남은 업무를 기준으로 방문 순서를 다시 계산한다.

재계획 입력에는 다음 정보가 포함된다.

- 현재 로봇 위치 및 진행 중인 목표
- 완료된 작업
- 진행 중인 작업
- 남은 작업
- 신규 작업
- 수거·전달 선후 관계
- 지점 간 이동 비용

기본 정책은 **진행 중인 작업을 완료한 후 다음 작업부터 신규 계획을 적용하는 것**이다.

동적 재계획은 다음 두 영역으로 구분한다.

| 구분 | 담당 | 책임 |
|---|---|---|
| 재계획 적용 정책 | A — 윤현수 | 요청 시점, 상태 보호, 계획 버전 검사, 실제 적용 승인 |
| 재계획 계산 알고리즘 | C — 이현수 | 남은 작업과 신규 주문을 반영한 방문 순서 재계산 |

A는 C가 계산한 계획이 현재 미션 상태와 일치하는지 확인한 뒤 실제 실행에 적용한다.

일시적 장애물은 Nav2의 주행·복구 기능으로 대응하고, 장시간 이동이 불가능한 상태는 Mission Manager가 오류 또는 관리자 확인 상태로 관리한다.

## 4. 핵심 연구 영역

본 프로젝트의 주요 기술적 성과는 다음 세 가지 연구에 집중한다.

| 연구 영역 | 비교 대상 | 주요 검증 지표 | 담당 |
|---|---|---|---|
| 연구 1. 전역 경로 탐색 | A* vs Dijkstra | 계산 시간, 경로 길이, 경로 생성 성공률 | B — 정지호 |
| 연구 2. 물류 방문 순서 최적화 | FIFO vs Greedy vs 완전탐색 | 총 거리·시간, 단축률, 계산 비용, 제약 준수 | C — 이현수 |
| 연구 3. 로컬 주행 제어 | DWB vs Regulated Pure Pursuit | 추종 오차, 주행 시간, 목표 도달 성공률, 안정성 | D — 홍근태 |

각 연구의 문제는 명확히 구분한다.

- **전역 경로 탐색:** 두 위치 사이의 경로를 어떻게 생성할 것인가?
- **물류 방문 순서 최적화:** 여러 작업을 어떤 순서로 처리할 것인가?
- **로컬 주행 제어:** 생성된 경로를 실제 로봇이 어떻게 따라갈 것인가?

세 연구의 결과를 연결하여 최종 미션의 성능을 분석하되, 실험 간 변수는 구분하여 관리한다.

B는 전역 경로 탐색 알고리즘을 연구하고, C는 해당 탐색 결과를 기반으로 계획 경로 비용표와 물류 방문 순서를 최적화하며, D는 계획 경로를 따라 실제 로봇을 주행시킨다.

## 5. 연구 1 — 전역 경로 탐색 알고리즘

**담당: B — 정지호**

### 5.1. 연구 목적

동일한 지도에서 A*와 Dijkstra의 경로 탐색 성능을 비교하고 실제 로봇의 운행 환경에 적합한 전역 플래너를 선정한다.

### 5.2. 비교 대상

| 알고리즘 | 특징 |
|---|---|
| A* | 목표까지의 추정 비용을 이용해 탐색 |
| Dijkstra | 출발점부터의 누적 비용을 기준으로 탐색 |

Nav2 Humble의 NavFn Planner와 `use_astar` 설정을 이용한 비교를 우선 검토한다.

두 알고리즘은 적절한 조건에서 동일한 최적 비용의 경로를 생성할 수 있으므로, A*의 경로가 반드시 더 짧다는 가정을 하지 않는다.

실제 비교에서는 계산 시간, 생성 경로, 탐색 성공률과 실차 주행 결과를 구분하여 평가한다.

### 5.3. 실험 시나리오

| R1-C | 좁은 통로·갈림길 | 탐색 효율 및 성공률 |

- 동일한 출발·목표 좌표

- 동일한 장애물 배치

## 6. 연구 2 — 물류 방문 순서 최적화

**담당: C — 이현수**

### 6.1. 연구 목적

여러 운반 업무를 처리할 때 방문 순서 결정 방식에 따른 이동 거리 및 실제 업무 시간을 비교하고 물류 효율 개선 효과를 검증한다.

프로젝트의 핵심 성능 연구 영역이다.

### 6.2. 비교 대상

| 방식 | 동작 |
|---|---|
| FIFO(입력 순서 기반) | 접수 순서를 기준으로 실행 가능한 작업을 처리 |
| Greedy(최근접 우선) | 현재 위치에서 이동 비용이 가장 낮은 실행 가능 지점 선택 |
| 완전탐색 | 제약 조건을 만족하는 모든 방문 순서를 검사 |

세 방식 모두 동일한 작업 선후 관계를 준수해야 한다.

FIFO 방식에서 접수 순서가 업무 선후 관계를 위반하는 경우, 사전에 정한 일관된 규칙으로 실행 가능한 기준 순서를 만든다.

Greedy 방식 역시 현재 실행 가능한 작업만 후보로 사용한다.

### 6.3. Nav2 계획 경로 기반 이동 비용표 생성

지점 간 이동 비용은 단순 직선거리가 아니라 Nav2 `ComputePathToPose`에서 생성한 **계획 경로**를 기반으로 계산한다.

반환된 `nav_msgs/Path`의 연속 좌표 사이 거리를 합산하여 계획 경로 길이를 산출한다.

이는 실제 로봇이 주행한 거리와 구분되는 값이다. 실제 이동 거리와 주행 시간은 별도 실차 실험에서 측정하여 계획 비용의 타당성을 검증한다.

| 출발/도착 | HOME | A | B | C | D |
|---|---|---|---|---|---|
| HOME | 0 | 계산 | 계산 | 계산 | 계산 |
| A | 계산 | 0 | 계산 | 계산 | 계산 |
| B | 계산 | 계산 | 0 | 계산 | 계산 |
| C | 계산 | 계산 | 계산 | 0 | 계산 |
| D | 계산 | 계산 | 계산 | 계산 | 0 |

방향에 따른 비용 차이를 고려하여 각 이동 방향을 독립적으로 계산한다.

고정 지점 간 비용 계산에서는 `ComputePathToPose`의 출발 자세(`start`), 목표 자세(`goal`), 출발 자세 사용 여부(`use_start`) 및 플래너 선택(`planner_id`)을 적절히 설정한다.

특히 고정된 두 지점의 비용을 계산할 때는 `use_start=true`로 지정한 출발 자세를 사용해야 하며, 실제 로봇의 현재 위치를 의도치 않게 사용하는 일이 없도록 검증한다.

**경로 비용 생성 및 활용 책임**

- **B:** 전역 경로 탐색 알고리즘 비교, 플래너 선정 및 계산 기준 제공
- **C:** 계획 경로 계산 요청, 지점 간 비용표 생성·저장·유효성 확인
- **D:** Nav2 Planner 실행 환경과 경로 계산 인터페이스의 가용성 확보

C는 D가 구성한 Nav2 Planner를 통해 계획 경로를 요청하고, B가 검증한 플래너 설정을 기준으로 비용표를 작성한다.

별도의 중계 노드를 반드시 거쳐야 하는 구조는 강제하지 않는다. 표준 Nav2 Action을 직접 호출하는 방식을 우선 검토한다.

각 지점의 출발·도착 자세가 실제 경로 계산과 호환되는지도 검증한다.

거리표는 사용한 지도, Costmap, 플래너 설정 및 지점 좌표의 버전과 함께 저장한다.

관련 설정이나 주행 가능 환경이 변경되면 기존 비용의 유효성을 확인하고 필요한 경로를 다시 계산한다.

### 6.4. 최적화 알고리즘

초기에는 HOME을 제외한 4개 작업 지점을 각각 한 번씩 방문하는 시나리오를 사용한다.

해당 조건에서 가능한 방문 순서의 최대 개수는 `4! = 24개`다.

초기 시나리오에 포함된 B 지점 수거 후 C 지점 전달이라는 선후 관계를 적용하면, 네 지점을 각각 한 번 방문하는 24개 순열 중 유효한 순열은 12개다.

단, 이는 해당 선후 관계 하나만 적용한 단순 방문 순열 기준이며 추가 업무 제약이 발생하면 유효 후보 수가 달라질 수 있다.

**처리 과정**

1. 후보 방문 순서 생성
2. 수거·전달 선후 관계 검사
3. 도달 불가능한 구간 제외
4. 후보별 전체 이동 비용 계산
5. HOME 복귀 비용 포함
6. 최소 비용 순서 선정

물류 업무를 완료하기 위해 동일 지점을 재방문해야 하는 확장 시나리오에서는 단순한 지점 순열이 아닌 작업 단계 기반 스케줄링이 필요하다.

향후 작업 지점이나 주문 수가 증가하는 경우 Held-Karp 또는 OR-Tools와 같은 확장 방식을 검토할 수 있다.

### 6.5. 실험 시나리오

| 실험 | 내용 |
|---|---|
| R2-A | 기본 다중 주문 처리 |
| R2-B | 수거·전달 선후 관계 포함 |
| R2-C | 동일 작업의 입력 순서 변경 |
| R2-D | 신규 주문 추가 후 재계획 |

### 6.6. 평가 지표

- 전체 계획 이동 거리(m)
- 실제 이동 거리(m)
- 총 주행 시간(s)
- 전체 미션 시간(s)
- 방문 순서 계산 시간(ms)

- 선후 관계 준수율(%)

**거리 단축률**

`(기준 경로 거리 - 최적화 경로 거리) / 기준 경로 거리 × 100`

순수 주행 시간과 작업자의 인계 대기 시간을 구분하여 기록한다.

각 방식에서 동일한 업무와 환경을 사용하며, 실제 주행은 같은 전역 플래너와 로컬 제어기로 비교한다.

계획 경로 길이와 실제 주행 거리를 같은 지표로 혼합하지 않는다.

### 6.7. 동적 재계획 알고리즘

C는 신규 주문 발생 시 남은 업무를 재배열하는 알고리즘을 구현한다.

**재계획 입력**

- 현재 로봇 위치 또는 계획 적용 기준 위치
- 완료된 작업 목록
- 진행 중인 작업 정보
- 대기 중인 작업
- 신규 등록 작업
- 수거·전달 선후 관계
- 지점 간 이동 비용
- 기준 계획 버전

**재계획 출력**

- 재계산한 방문 순서
- 예상 총 이동 비용
- 반영한 작업 목록
- 기준 계획 버전
- 계산 결과의 성공·실패 여부

C는 계산 결과를 A에 반환한다.

A가 재계획 결과를 실제로 적용할지 결정하며, 적용 이전에 완료 상태나 진행 중인 작업이 변경되었을 경우 재검증 또는 재계산을 요청한다.

기본 재계획 기능은 P0 필수 구현에 포함한다.

## 7. 연구 3 — 로컬 주행 제어 알고리즘

**담당: D — 홍근태**

### 7.1. 연구 목적

같은 전역 경로를 주행할 때 로컬 제어기의 경로 추종 정확도, 소요 시간, 도달 성공률 및 안정성을 비교한다.

### 7.2. 비교 대상

| 제어기 | 특징 |
|---|---|
| DWB | 속도 후보와 주행 궤적의 평가를 기반으로 제어 명령 생성 |
| Regulated Pure Pursuit | 경로 추종과 곡률·속도·충돌 관련 제한을 함께 고려 |

ROS2 Humble 환경에서 실제 설치 및 구동 가능한 버전을 기준으로 비교한다.

### 7.3. 실험 조건

- 동일한 로봇 및 지도
- 동일한 출발·목표 자세
- 동일한 사전 계산 전역 경로
- 동일한 안전 제한 및 최대 속도
- 동일한 장애물 배치
- 동일한 측정 방식
- 제어기별 설정 파일 및 버전 기록

가능하다면 동일한 `nav_msgs/Path`를 `FollowPath` 액션에 전달하고 제어기를 선택하여 비교한다.

각 제어기의 내부 설정값은 차이가 있으므로 모든 수치를 억지로 동일하게 만드는 대신 공통 안전 조건을 유지하고 개별 튜닝 내용을 기록한다.

### 7.4. 실험 시나리오

| 실험 | 환경 | 평가 내용 |
|---|---|---|
| R3-A | 직선 주행 | 추종 오차 및 주행 시간 |
| R3-B | 연속 회전 | 회전 안정성 |
| R3-C | 장애물 근접 경로 | 속도 변화 및 안전성 |
| R3-D | 실제 물류 경로 | 전체 주행 성능 |

### 7.5. 평가 지표

- 목표 지점 도달 성공률(%)
- 주행 시간(s)
- 실제 이동 거리(m)
- 평균 경로 추종 오차(m)
- 최대 추종 오차(m)
- 비정상 정지 및 복구 횟수
- 반복 실험 간 성능 편차

경로 추종 오차는 사용한 위치 추정 데이터의 정확도에 영향을 받으므로, 측정 방법과 한계를 명시한다.

### 7.6. 도착 정밀 정렬

D는 일반적인 Nav2 목표 도달 이후 물품 인계에 적합한 로봇 자세를 확보하는 기능을 검토한다.

- 목표 위치 및 방향 오차 확인
- 실제 작업 지점의 정렬 요구사항 검토
- 필요 시 ArUco 기반 상대 위치·방향 보정
- 정렬 성공·실패 판정 및 A에 결과 전달

카메라 및 마커의 설치·고정과 기본 영상 수신 환경은 C가 담당한다.

D는 해당 센서 데이터를 이용한 정렬 알고리즘과 주행 동작을 담당한다.

도착 정밀 정렬은 기본 Nav2 주행과 구분하며, 실차 테스트를 통해 필요성과 구현 범위를 결정한다.

정밀 정렬 기능을 적용하지 않더라도 기본 물류 미션이 완료될 수 있도록 설계한다.

## 8. 동적 재계획 및 예외 처리

### 8.1. 기본 동적 재계획 — P0 필수

1. E에서 신규 주문 접수
2. A가 현재 미션 상태 확인
3. A가 완료·진행 중·대기 작업 구분
4. A가 C에 재계획 요청
5. C가 신규 주문과 대기 작업 통합
6. C가 선후 관계 및 이동 비용 검사
7. C가 남은 방문 순서 최적화
8. C가 계획 결과와 기준 버전 반환
9. A가 최신 상태와 결과 일치 여부 검사
10. A가 현재 작업 완료 후 안전한 시점에 변경 계획 적용
11. D가 새로운 방문 순서에 따른 주행 수행
12. E가 변경 계획과 실행 상태 표시

현재 주행 목표를 임의로 반복 취소하지 않는다.

계획은 버전으로 관리하며, 이전 계산 결과가 늦게 도착하더라도 최신 계획을 덮어쓰지 않도록 한다.

P0에서는 진행 중인 작업을 정상 완료한 뒤 다음 작업부터 새 계획을 적용하는 기본 기능을 구현한다.

### 8.2. A와 C의 책임 구분

| 항목 | A — Mission Manager | C — Route Optimizer |
|---|---|---|
| 신규 주문 접수 후 처리 | 상태 확인·재계획 요청 결정 | 계산 요청 수신 |
| 완료된 작업 | 완료 상태 보존 | 계산에서 제외 |
| 진행 중인 작업 | 실행 상태 보호 | 고정 조건으로 반영 |
| 재계획 알고리즘 | 적용 정책 결정 | 방문 순서 계산 |
| 계획 버전 | 최신성 검사 및 적용 버전 관리 | 기준 버전 포함 결과 반환 |
| 실제 주행 변경 | 적용 시점 승인 및 D에 요청 | 주행 직접 제어하지 않음 |
| 계산 실패 | 미션 상태·오류 관리 | 실패 원인 반환 |

**C는 계획을 계산하고, A는 계획의 실행을 책임진다.**

### 8.3. 예외 처리 기준

| 상황 | 기본 처리 | 주요 책임 |
|---|---|---|
| 물품 인계 지연 | 정지 상태로 확인 대기 | A·E |
| 작업자 확인 취소 | 상태 재확인 후 처리 | A·E |
| 목적지 주행 실패 | 안전 정지·재시도 또는 오류 전환 | D·A |
| 목표 경로 없음 | 해당 작업 보류 및 관리자 알림 | B·D·A |
| 방문 순서 계산 불가 | 오류 반환 및 유효한 기존 계획 유지 여부 판단 | C·A |
| 위치 추정 불량 | 주행 중단 및 위치 확인 | D·A |
| 센서·Bringup 장애 | 장비 상태 확인 및 복구 | C |
| 통신 단절 | 연결 끊김 표시 및 안전 복구 절차 | C·D·A·E |
| 비상정지 | 기존 E-Stop 유지, 명시적 복구 절차 | C·D·A |

실제 안전 정지 및 복구 동작은 기존 로봇 하드웨어와 ROS2 구동 환경의 지원 여부를 확인한 뒤 검증한다.

웹에서 연결 상태가 바뀌었다는 이유만으로 로봇이 안전하게 정지했다고 단정하지 않는다.

### 8.4. 고급 예외 처리 — P1

다음 기능은 기본 동적 재계획과 구분하여 P1에서 고도화한다.

- 재계획 계산 타임아웃 및 재시도 정책
- 복수 신규 주문 동시 접수 시 충돌 처리
- 실패 작업의 보류·복구·재실행 정책
- 주행 불가 상황에서의 관리자 개입 및 미션 복구
- 재계획 전후 실행 로그 자동화
- 복잡한 다중 작업 재방문 시나리오

P1의 고도화 기능이 없어도 P0에서 기본 신규 주문 재계획을 시연할 수 있어야 한다.

## 9. 시스템 아키텍처

### 9.1. 주요 구성

**상위 물류 미션 처리 흐름**

1. **Web Dashboard / Order Manager — E**
   - 사용자 작업 등록
   - 신규 주문 및 인계 확인
   - 진행 상태와 실험 결과 표시

2. **Mission Manager — A**
   - 작업 검증 및 미션 상태 관리
   - 방문 순서 최적화 요청
   - 재계획 적용 정책
   - 미션 실행 및 예외 처리

3. **Route Optimizer — C**
   - Nav2 계획 경로 기반 이동 비용표
   - FIFO·Greedy·완전탐색
   - 최적 방문 순서 계산
   - 신규 주문 재계획 계산

4. **Mission Executor — A**
   - 작업 지점별 이동 요청
   - 주행 결과 수신
   - 물품 인계 대기 및 완료 처리
   - 다음 작업과 HOME 복귀 실행

5. **AMR Navigation / Nav2 — D**
   - Nav2·AMCL
   - 목표 이동 및 주행 피드백
   - 로컬 제어 및 주행 안정화
   - 필요 시 정밀 정렬

**지원 시스템**

- **Global Planner Research — B:** A*·Dijkstra 비교, 전역 플래너 선정·검증
- **Robot Bringup — C:** 하드웨어, 센서, 드라이버, TF 및 ROS2 기본 실행환경

**핵심 데이터 흐름**

`E → A → C → A → D`

B는 전역 경로 탐색 연구 및 선정 결과를 D의 Nav2 Planner 구성에 반영하고, C의 이동 비용표 계산에 필요한 플래너 기준을 제공한다.

C는 D가 관리하는 Nav2 Planner 환경에서 계획 경로 비용을 계산한다.

C는 하드웨어·Bringup과 물류 최적화를 모두 담당하지만, 두 기능은 소프트웨어 구조에서 서로 분리하여 관리한다.

각 단계의 작업 상태와 실행 결과는 E의 DB 및 웹 관제로 전달한다.

### 9.2. 주행 실행 방식

초기에는 `NavigateToPose`를 사용하여 지점별 이동을 요청하는 구조를 우선 검토한다.

하나의 작업 지점에서 도착 확인과 물품 인계 대기를 관리해야 하므로, Mission Manager가 지점별 실행 상태를 유지하도록 설계한다.

Nav2 `FollowWaypoints`도 사용 가능하지만, 초기 버전에서는 복수 지점 이동과 물류 작업 완료 판정을 분리하는 방식을 우선한다.

알고리즘 비교 실험에서는 `ComputePathToPose`와 `FollowPath`를 목적에 맞게 사용한다.

### 9.3. 주요 모듈의 책임 경계

| 모듈 | 담당 | 직접 관리하는 영역 |
|---|---|---|
| Mission Manager | A | 미션·작업 상태, 실행 승인, 재계획 적용 정책 |
| Global Planner Research | B | A*·Dijkstra 비교, 전역 플래너 검증 |
| Route Optimizer | C | 계획 경로 비용표, 방문 순서 최적화, 재계획 계산 |
| Robot Bringup | C | 하드웨어, 센서·드라이버, TF 및 기본 ROS2 실행 |
| AMR Navigation | D | Nav2·AMCL, 목표 이동, Controller, 정밀 정렬 |
| Web Control | E | 작업 입력·인계 UI, 상태 표시, 데이터 저장 |

동일 담당자가 맡더라도 `route_optimizer`와 `amr_bringup`은 별개의 책임 영역으로 구성한다.

**권장 관리 항목**

- ROS2 패키지별 담당 범위
- 인터페이스 및 데이터 계약

- 버전 관리된 Nav2 설정
- 하드웨어·센서 설정
- 알고리즘별 실험 데이터 및 분석 코드
- 실행·복구 매뉴얼
- 통합 테스트 기록

**초기 ROS2 패키지 구성 후보**

| 패키지 | 담당 | 목적 |
|---|---|---|
| `logistics_msgs` | A 관리, 팀 공통 | 공통 메시지·서비스 |
| `mission_manager` | A | 작업·미션 상태 및 실행 |
| `route_optimizer` | C | 계획 경로 비용표, 방문 순서 최적화, 재계획 계산 |
| `amr_navigation` | D | Nav2·AMCL, 주행 및 로컬 제어 |
| `amr_bringup` | C | 하드웨어·센서·TF·로봇 기본 실행 |
| 전역 플래너 비교 코드·도구 | B | A*·Dijkstra 실험 및 검증 |

B의 전역 플래너 비교 기능은 기존 Nav2 패키지의 설정·실험 도구로 충분한지 먼저 검토하고, 독립 ROS2 패키지가 필요한 경우에만 추가한다.

C는 `route_optimizer`와 `amr_bringup`을 모두 담당하지만 두 패키지는 분리한다.

Nav2 Planner와 Controller의 설정은 D가 관리하고, 실제 하드웨어·센서 관련 설정은 C가 관리한다.

E의 FastAPI 및 웹 기능은 `web_control/` 영역에 둔다.

한 대의 실제 로봇을 공유하므로 실차 테스트 시간을 팀 간 조율하고, 안정적인 실행 버전을 별도로 유지한다.

## 11. 최종 5인 역할 분담

| 담당 | 분야 | 핵심 책임 | 최종 산출물 |
|---|---|---|---|
| **A — 윤현수** | 팀장·시스템 통합 | Mission Manager, 상태 머신, 미션 실행, 동적 재계획 적용 정책, 시스템 통합 | 미션 실행기, 상태 관리, 통합 시스템 |
| **B — 정지호** | 전역 경로 탐색 | A*·Dijkstra 성능 비교, 전역 경로 탐색 최적화 | 경로 탐색 비교 모듈, 성능 실험 결과, 알고리즘 선정 근거 |
| **C — 이현수** | 물류 방문 순서 최적화·하드웨어 | 계획 경로 비용표, FIFO·Greedy·완전탐색, 동적 재계획 알고리즘, 하드웨어·Bringup | 방문 순서 최적화 모듈, 재계획 기능, 로봇 기본 구동 환경 |
| **D — 홍근태** | 자율주행·로컬 제어 | DWB·RPP 성능 비교, Nav2·AMCL, 주행 안정화, 도착 정밀 정렬 | 주행 제어 모듈, Controller 설정, 실주행 검증 결과 |

### 11.1. A — 윤현수 / 팀장·시스템 통합

## 12. 시험·검증 및 기술 선정 운영

### 12.1. 검증 책임

별도의 시험·검증 전담자를 두지 않는다.

각 담당자가 다음 과정을 직접 수행한다.

**후보 구현 → 비교 실험 → 결과 분석 → 선정 근거 작성 → 최종 적용 → 재검증**

- **A:** 상태 머신, 재계획 적용 정책 및 통합 미션 검증
- **B:** A*·Dijkstra 전역 경로 탐색 검증
- **C:** FIFO·Greedy·완전탐색, 재계획 알고리즘, 하드웨어·Bringup 검증
- **D:** DWB·RPP 비교, Nav2·AMCL 및 실차 주행 검증
- **E:** 웹 기능, DB 및 실험 데이터 정확성 검증

### 12.2. 실험의 공정성

- 동일한 지도와 작업 좌표 사용
- 동일한 장애물 조건 유지
- 비교 대상 외 설정은 가능한 한 고정
- 소프트웨어 및 설정 버전 기록
- 반복 측정 실시
- 성공 및 실패 데이터 모두 포함
- 평균·편차·성공률 등으로 결과 분석
- 시뮬레이션과 실차 결과 구분

실차 실험은 초기 기능 검증 후 조건별 5회 이상을 기준으로 하고, 최종 주요 실험은 가능하면 10회 반복한다.

순서에 따른 배터리 상태나 환경 차이를 줄이기 위해 비교 실험의 수행 순서도 기록하거나 교차 배치한다.

### 12.3. 공통 기록 항목

| 항목 | 내용 |
|---|---|
| `experiment_id` | 실험 식별자 |
| `scenario_id` | 실험 환경 |
| `run_mode` | MOCK / SIM / REAL |
| `algorithm` | 적용 기술 |
| `config_version` | 설정 버전 |
| `map_version` | 지도 버전 |
| `planner_id` | 사용 전역 플래너 |
| `controller_id` | 사용 로컬 제어기 |
| `planned_distance` | 계획 경로 이동 거리 |
| `actual_distance` | 실제 주행 거리 |
| `planning_time` | 계산 시간 |
| `execution_time` | 주행 시간 |
| `goal_success` | 목표 도달 여부 |
| `mission_success` | 미션 완료 여부 |
| `failure_reason` | 실패 원인 |

측정 기준과 단위를 명확히 정의하여 저장한다.

계획 경로 길이와 실제 이동 거리는 서로 다른 데이터로 관리한다.

### 12.4. 기술 선정 보고서

각 연구 담당자는 다음 내용을 정리한다.

1. 문제 상황
2. 비교 후보 및 선정 이유
3. 실험 환경과 통제 조건
4. 측정 결과 및 그래프
5. 결과 차이와 실패 원인 분석
6. 최종 선정 기술
7. 선택 근거
8. 실제 시스템 적용 결과
9. 한계 및 후속 개선 사항

측정되지 않은 성능이나 예상 단축률을 실제 결과처럼 제시하지 않는다.

### 12.5. Sim-to-Real 검증 원칙

시뮬레이션에서 정상 동작한 기능도 실차에서 별도로 검증한다.

실차 검증은 다음 순서를 기준으로 진행한다.

| 단계 | 검증 내용 | 주요 담당 |
|---|---|---|
| Gate 0 | 센서·통신·TF·Odometry 및 기본 Bringup | C |
| Gate 1 | 저속 직진·회전·정지 및 기본 구동 | C·D |
| Gate 2 | Nav2 단일 목표 주행 | D, C 지원 |
| Gate 3 | 복수 지점 이동 및 HOME 복귀 | D·A |
| Gate 4 | 작업 등록·최적화·인계 확인 통합 | A·C·D·E |
| Gate 5 | 신규 주문 재계획 및 최종 미션 | 전체 |

실차 주행 준비 상태는 다음 두 영역으로 구분한다.

- **Hardware/Bringup Readiness — C:** 센서·드라이버·TF·통신·로봇 구동 환경
- **Navigation Readiness — D:** AMCL·Nav2 Lifecycle·Planner·Controller 및 자율주행 준비 상태

A는 해당 상태를 확인한 뒤 Mission Manager의 주행 요청 허용 여부를 결정한다.

주행 중에도 센서·위치 추정·안전 상태 변화에 대한 감시가 필요하며, Readiness 검사를 통과했다는 이유만으로 안전이 지속해서 보장된다고 가정하지 않는다.

**검증 성과:** A의 상태 머신과 D의 자율주행 통합

A는 새로운 계획을 검증하고, 진행 중인 작업을 완료한 뒤 다음 작업부터 계획을 적용한다.

**검증 성과:** A·C의 동적 미션 관리 및 작업 스케줄링

### 시연 4 — 알고리즘 비교 결과

사전에 반복 측정한 세 가지 연구 영역의 결과를 보여준다.

**검증 성과:** 객관적인 데이터 기반 기술 선정

## 17. AI 기반 개발 및 팀 협업 지침

팀원마다 개별 AI 개발 도구를 사용하더라도 공통 설계를 유지할 수 있도록 다음 원칙을 적용한다.

### 17.1. 공통 기준

1. 본 문서를 프로젝트의 상위 요구사항으로 사용한다.
2. 맡은 모듈의 책임과 완료 기준을 우선한다.
3. 실제 로봇 및 저장소의 현재 상태를 확인한 뒤 개발한다.
4. 다른 담당 영역의 코드를 임의로 변경하지 않는다.
5. 공통 데이터 모델과 인터페이스 변경은 팀 합의를 거친다.
6. 기존 ROS2 Humble 및 Nav2 환경과 호환되는 구현을 우선한다.
7. 검증하지 않은 알고리즘을 최종 채택 기술로 단정하지 않는다.
8. 실험하지 않은 결과나 성능 수치를 생성하지 않는다.
9. IoT·적재 용량 판단·자동 집게 등 제외 기능을 임의로 추가하지 않는다.
10. 구현 결과, 실행 방법, 테스트 결과 및 미해결 문제를 기록한다.

### 17.2. TCREI 기반 AI 작업 지시

**Task — 작업**

담당 모듈과 구현 목표, 완료 기준을 정의한다.

**Context — 맥락**

본 기획서, 기존 저장소, 실제 로봇 구성 및 현재 개발 상태를 제공한다.

**Reference — 참고자료**

공식 ROS2·Nav2 문서, 팀에서 합의한 인터페이스 및 기존 검증 자료를 제공한다.

**Evaluate — 검증**

기능 테스트, 알고리즘 실험, 실차 검증 및 결과 기록을 수행한다.

**Iterate — 개선**

실험 결과에 따라 수정하고, 변경 전후의 차이와 선택 근거를 문서화한다.

### 17.3. 팀원별 AI 작업 요청 시 필수 명시 사항

- 담당자 역할(A~E)
- 현재 개발 단계(P0/P1/P2)
- 실제 저장소 및 작업 환경
- 관련 공통 인터페이스
- 구현 범위와 변경 금지 영역
- 검증 방법과 완료 조건
- 필요한 다른 담당자와의 협업 사항

특히 다음 구분을 준수한다.

- B의 전역 경로 탐색과 C의 물류 방문 순서 최적화를 혼동하지 않는다.
- A의 재계획 적용 정책과 C의 재계획 알고리즘을 구분한다.
- C의 하드웨어·Bringup 책임과 D의 Nav2 자율주행 책임을 구분한다.
- C가 담당하는 `route_optimizer`와 `amr_bringup`을 서로 다른 소프트웨어 영역으로 관리한다.
- E가 Mission Manager의 상태를 독자적으로 변경하지 않는다.

각 AI는 본 기획서에서 아직 정하지 않은 Topic, Service, Action, 파일·패키지 이름을 확정된 표준처럼 가정하지 않아야 한다.

### 17.4. 작업 결과 공유 기준

모든 담당자는 다음 내용을 공유한다.

- 구현 및 변경한 기능
- 주요 수정 파일
- 실행 및 테스트 방법
- 측정 결과와 실패 사례
- 변경된 인터페이스
- 미해결 문제
- 통합에 필요한 사항
- 다음 작업

### 17.5. 공통 인터페이스 변경 원칙

공통 인터페이스는 다음 기준으로 관리한다.

- A가 미션 상태 및 작업 데이터 계약을 관리한다.
- B는 전역 플래너의 실행·선정 기준을 제공한다.
- C는 방문 순서 최적화 및 재계획 계산의 입력·출력 계약을 제공한다.
- C는 하드웨어·센서·Bringup 환경과 관련 설정을 관리한다.
- D는 Nav2 주행 및 계획 경로 계산 인터페이스를 제공한다.
- E는 웹 API와 DB 데이터 계약을 제공한다.

공통 인터페이스 변경 시 영향을 받는 담당자와 합의한 뒤 반영한다.

## 18. 기대 성과 및 최종 제안

### 18.1. 물류 최적화

복수 물류 작업의 방문 순서를 **Nav2 계획 경로 기반 이동 비용**으로 최적화하고, 실제 주행 결과와 비교하여 기준 방식 대비 이동 거리와 주행 시간을 정량적으로 분석한다.

### 18.2. 데이터 기반 기술 선정

전역 경로 탐색, 물류 방문 순서 최적화, 로컬 주행 제어의 세 가지 연구에서 직접 비교 실험을 수행하고 선택 근거를 제시한다.

### 18.3. 동적 작업 관리

신규 주문 발생 시 현재 작업 상태를 보존하면서 남은 업무를 재계획하는 상위 미션 관리 구조를 구현한다.

A는 재계획 정책과 실행 상태를 관리하고, C는 새로운 방문 순서를 계산한다.

기본 동적 재계획은 P0에 포함하고, 복잡한 실패 복구와 예외 처리는 P1에서 고도화한다.

### 18.4. 통합 시스템 개발

ROS2 기반 하드웨어·Bringup, 전역 경로 탐색, 물류 방문 순서 최적화, 자율주행 및 중앙 웹 관제를 분리 개발하고 공통 인터페이스로 통합한다.

### 18.5. 문제 해결 및 검증 역량

기능 구현 결과뿐 아니라 실험 설계, 성능 측정, 실패 분석, 기술 선택 및 개선 과정을 기록해 재현 가능한 기술 성과를 제시한다.

### 최종 목표
