## 3. 최종 팀원 역할

| 담당 | 이름 | 주요 책임 |
|---|---|---|
| A | 윤현수 | Mission Manager, 상태 머신, 재계획 적용 정책, 시스템 통합 |
| B | 정지호 | A*·Dijkstra 전역 경로 탐색 비교 및 최적화 |
| C | 이현수 | 방문 순서 최적화, 동적 재계획 계산, 하드웨어·Bringup |
| D | 홍근태 | Nav2·AMCL, DWB·RPP, 자율주행, 정밀 정렬 |
| E | 강연주 | 웹 관제, FastAPI, SQLite, 실험 데이터 시각화 |

### 책임 경계

- **A:** 계획을 요청하고 실제 실행에 적용한다.
- **B:** 두 지점 사이의 전역 경로 탐색을 연구한다.
- **C:** 여러 작업의 방문 순서를 계산하고 하드웨어·Bringup을 전담한다.
- **D:** 실제 로봇의 Nav2 주행을 담당한다.
- **E:** 작업자 입력, 관제 및 데이터 저장을 담당한다.

C의 하드웨어·Bringup과 물류 최적화는 서로 다른 소프트웨어 영역으로 관리한다.

역할과 공통 아키텍처의 변경은 A가 승인한다.

## 4. 물류 업무 모델

초기 시연은 HOME과 4개 작업 지점을 이용한다.

| 업무 | 내용 |
|---|---|
| JOB-001 | HOME → A |
| JOB-002 | B → C |
| JOB-003 | D → HOME |

작업자는 물품을 직접 적재·하역하고, 웹에서 인계 완료를 확인한다.

**데이터 모델**

- `Job`: 하나의 물류 업무
- `TaskStep`: 수거·전달 등의 실행 단계
- `Waypoint`: 물리적 방문 지점
- `Mission`: 전체 작업 실행 상태
- `RoutePlan`: 방문 순서와 예상 비용
- `RobotStatus`: 로봇 준비·주행 상태
- `ExperimentResult`: 실험 조건 및 측정 결과

**필수 제약**

1. 수거 이전에 해당 물품을 전달하지 않는다.
2. 목표 도착만으로 작업을 완료 처리하지 않는다.
3. 인계 확인 이후에만 해당 TaskStep을 완료한다.
4. 완료된 작업을 중복 실행하지 않는다.
5. 현재 진행 중인 작업 상태를 보호한다.
6. 모든 필수 작업 이후 HOME으로 복귀한다.
7. HOME 최종 하역이 필요한 경우 확인 후 미션을 종료한다.

## 5. 시스템 아키텍처

### 기본 패키지

| 패키지·영역 | 담당 | 목적 |
|---|---|---|
| `logistics_msgs` | A 관리 | 공통 ROS2 인터페이스 |
| `mission_manager` | A | 미션·작업 상태 및 실행 관리 |
| 전역 플래너 연구 코드 | B | A*·Dijkstra 비교 |
| `route_optimizer` | C | 경로 비용표·방문 순서·재계획 계산 |
| `amr_bringup` | C | 하드웨어·센서·기본 구동환경 |
| `amr_navigation` | D | Nav2·AMCL 및 실제 주행 |
| `web_control` | E | 웹 UI·API·DB |

### 핵심 업무 흐름

**E → A → C → A → D → A → E**

1. E에서 작업 접수
2. A에서 작업 검증
3. C에서 방문 순서 계산
4. A에서 계산 결과 검증·승인
5. D에서 실제 이동
6. A에서 도착 결과 처리
7. E에서 인계 확인 요청
8. A에서 작업 완료 및 다음 단계 실행

**보조 연동**

- B → D: 전역 플래너 설정·실험 결과
- B → C: 계획 경로 계산 기준
- C → Nav2: `ComputePathToPose` 기반 경로 비용 계산
- C Bringup → D: 센서·TF·Odometry·기본 구동환경

표준 ROS2·Nav2 인터페이스를 우선 재사용한다.

불필요한 중계 노드나 사용자 정의 Action을 추가하지 않는다.

## 6. 핵심 연구 영역

### 연구 1 — 전역 경로 탐색 (B)

**비교:** A* vs Dijkstra

**주요 지표**

- 경로 계산 시간
- 경로 길이
- 경로 생성 성공률
- 실차 주행 검증 결과

Nav2 Jazzy의 NavFn Planner를 이용한 비교를 우선 검토한다.

최종 플래너 선정 결과는 C·D에게 공유한다.

### 연구 2 — 물류 방문 순서 최적화 (C)

**비교:** FIFO vs Greedy vs 완전탐색

**주요 지표**

- 계획 이동 거리
- 실제 이동 거리
- 계산 시간
- 실제 주행 시간
- 거리·시간 단축률
- 선후 관계 준수율

Nav2 `ComputePathToPose`의 계획 경로를 이용하여 지점 간 이동 비용표를 작성한다.

계획 경로 거리는 실제 주행 거리와 구분한다.

초기 4개 지점의 단순 순열은 최대 24개이며, B 수거 후 C 전달이라는 선후 관계만 적용하면 12개 순열이 유효하다.

완전탐색은 초기 소규모 시나리오의 최적해 검증 기준으로 사용한다.

### 연구 3 — 로컬 제어 (D)

**비교:** DWB vs Regulated Pure Pursuit

**주요 지표**

- 경로 추종 오차
- 목표 도달 성공률
- 주행 시간
- 주행 안정성
- 실패 및 복구 횟수

가능한 한 동일한 계획 경로를 사용해 비교한다.

최종 기술 채택은 실험 결과를 근거로 결정한다.

## 7. 동적 재계획 — Priority P0 필수

기본 정책은 **현재 진행 중인 작업을 완료한 뒤 새로운 방문 계획을 적용하는 것**이다.

**C — 계산**

- 완료된 작업 제외
- 진행 중인 작업 조건 반영
- 신규 주문 포함
- 선후 관계 검증
- 남은 방문 순서 계산
- 기준 계획 버전 반환

**A — 적용**

- 최신 미션 상태 확인
- 계획 버전 일치 여부 검사
- 진행 중인 작업 보호
- 새 계획 적용 시점 결정
- D에 다음 목표 이동 요청

오래된 계산 결과가 최신 계획을 덮어쓰지 않도록 한다.

고급 예외 복구, 복수 재계획 충돌 및 복잡한 재방문 정책은 Priority P1에서 고도화한다.

## 9. Sim-to-Real 및 안전

### 실행환경

| 모드 | 목적 |
|---|---|
| MOCK | 상태 머신과 인터페이스 검증 |
| SIM | Gazebo Harmonic 기반 주행 검증 |
| REAL | 실제 TurtleBot3 주행 검증 |

`use_sim_time`은 시간 기준 설정이며, DDS 통신환경 격리의 대체 수단이 아니다.

### 준비 상태

- **C:** Hardware/Bringup Readiness
- **D:** Navigation Readiness
- **A:** Mission Execution Readiness

필수 준비 상태가 FAIL 또는 UNKNOWN이면 자동 주행을 시작하지 않는다.

### 실차 Gate

| Gate | 검증 목표 | 담당 |
|---|---|---|
| 0 | 센서·TF·통신·Bringup | C |
| 1 | 기본 저속 구동·정지 | C·D |
| 2 | Nav2 단일 목표 | D, C 지원 |
| 3 | 다중 지점·HOME 복귀 | A·D |
| 4 | 물류 미션 통합 | A·C·D·E |
| 5 | 신규 주문 동적 재계획 | 전체 |

Gate의 실제 PASS 여부는 실차 시험과 증빙을 통해 확인한다.

기존 실차 개발 경험에서 확인된 TF Timeout, AMCL 정합 불량, Controller 비활성 및 경로 생성 후 주행 불가 사례를 초기 위험 검토에 활용한다.

이전 프로젝트에서 발생한 문제를 현재 프로젝트에서 이미 발생한 오류로 단정하지 않는다.

### Jazzy 실차 전환 확인 사항

실차의 ROS2 Jazzy 적용 전 다음을 확인한다.

- TurtleBot3 컴퓨팅 보드 모델 및 아키텍처
- 실제 로봇에 적용할 Ubuntu 버전
- TurtleBot3 Jazzy 패키지 및 드라이버 지원
- OpenCR 펌웨어와 모터 구동 호환성
- LiDAR·카메라 등 센서 드라이버
- 개발 PC와 로봇 간 DDS 통신
- TF·Odometry·AMCL·Nav2 실행 상태
- 안전 정지와 복구 절차

실차 OS 또는 펌웨어 변경은 백업 및 복구 방법을 확인하고 담당자 간 합의한 뒤 수행한다.

## 10. 인터페이스 및 데이터 관리

- Job·TaskStep·Mission의 상태는 A가 관리한다.
- C는 방문 순서를 계산하고 결과를 반환한다.
- D는 실제 주행 결과를 제공한다.
- E는 인계 요청과 관제 화면을 관리한다.
- B는 전역 플래너 선정 기준을 제공한다.
- 실험 결과는 우선 JSON·CSV·SQLite에서 관리한다.
- 공통 ROS2 메시지는 필요한 경우에만 추가한다.
- ROS2 Jazzy·Nav2 표준 인터페이스를 우선 재사용한다.
- 센서 Topic은 실제 Publisher와의 QoS 호환성을 우선한다.
- 상태 정보의 Reliable·Transient Local 사용 여부는 데이터 특성에 따라 결정한다.
- 요청 타임아웃·중복 처리·재시도·취소 정책은 실험과 환경 확인 후 구체화한다.

정확한 Topic·Service·Action 이름과 사용자 정의 필드는 `docs/INTERFACES.md` 및 승인된 기술 결정에 따른다.

미확정 세부사항은 임의로 확정하지 않는다.

## 12. Codex 개발 지침

### 작업 전

1. `AGENTS.md`와 현재 작업 관련 문서를 읽는다.
2. 기존 저장소와 코드 상태를 확인한다.
3. 승인된 아키텍처와 기술 결정을 확인한다.
4. 실제 환경에서 확인하지 못한 사항을 구분한다.
5. 영향을 받는 담당자와 인터페이스를 식별한다.
6. SSH 원격 작업 시 Ubuntu 프로젝트 경로와 ROS2 실행환경을 확인한다.

### 개발 중

- 담당 모듈의 책임 경계를 유지한다.
- 최소 구현을 우선한다.
- 기존 ROS2·Nav2 표준 기능을 재사용한다.
- 다른 담당자의 코드를 임의로 변경하지 않는다.
- 공통 인터페이스 변경은 A의 승인을 받는다.
- 실제 측정값을 생성하거나 추측하지 않는다.
- 구현된 기능과 미구현 기능을 구분한다.
- Mac 로컬 저장소와 Ubuntu 원격 저장소를 혼동하지 않는다.
- ROS2 패키지의 빌드와 테스트는 Jazzy 환경에서 수행한다.

### 검증 후

- 변경 파일을 기록한다.
- 실행한 테스트와 결과를 보고한다.
- 미실행 검증을 명시한다.
- 미해결 사항을 기록한다.
- 다음 단계의 최소 작업을 제안한다.

### 승인 및 실행 범위

아키텍처 v1.0은 승인된 상태다.

다만 승인된 설계가 모든 세부 통신 계약이나 실제 구현 완료를 의미하지 않는다.

읽기 전용 설계·검증 요청에서 임의로 파일을 수정하지 않는다.

사용자가 명시적으로 구현을 요청한 경우에는 승인된 책임 경계 안에서 구현과 검증을 진행한다.
