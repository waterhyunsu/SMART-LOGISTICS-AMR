# 시스템 인터페이스 계약 — SMART-LOGISTICS AMR

> **문서 상태:** 초기 인터페이스 설계 기준 v1.0  
> **아키텍처 기준:** 승인된 초기 아키텍처 v1.0  
> **최종 승인권자:** A — 윤현수 (팀장)  
> **최상위 요구사항:** `docs/reference/ORIGINAL_PROPOSAL.md`  
> **관련 문서:** `docs/PRD.md`, `docs/ARCHITECTURE.md`  
> **기준일:** 2026-11-17  
> **공통 개발 기준:** ROS2 Jazzy / Nav2 (Ubuntu 24.04)

본 문서는 SMART-LOGISTICS AMR에서 팀원별 모듈 간 정보 교환, 데이터 소유권, 상태 전이 및 오류 처리의 공통 기준을 정의한다.

팀원별 책임과 데이터 흐름은 승인된 아키텍처를 따른다. A↔C 생성 타입과 필드는 §6에서 확정했다. 웹 API 경로와 미정인 런타임 이름은 별도로 결정한다.

**표기 기준**

- **[확정]** 최종 기획서 및 승인된 아키텍처에서 결정된 사항
- **[설계 후보]** 구현 방식의 제안으로, 세부 결정이 필요한 사항
- **[미확인]** 실제 로봇 또는 개발환경에서 확인하지 못한 사항

---

## 1. 인터페이스 설계 원칙

1. ROS2 Jazzy·Nav2 표준 인터페이스를 우선 사용한다.
2. 불필요한 사용자 정의 Topic·Service·Action을 추가하지 않는다.
3. Job, TaskStep, Waypoint, Mission의 ID와 상태를 구분한다.
4. 모든 작업 완료 판정은 Mission Manager가 수행한다.
5. 목표 위치 도착을 물품 인계 완료로 간주하지 않는다.
6. 신규 주문에 따른 재계획 계산과 실제 적용을 분리한다.
7. 비동기 계산 결과가 최신 실행 상태를 덮어쓰지 않도록 한다.
8. 실패·타임아웃·중복 요청을 정상 완료로 처리하지 않는다.
9. MOCK / SIM / REAL 환경에서 가능한 한 동일한 상위 계약을 사용한다.
10. 구현된 인터페이스와 실제 테스트 결과를 문서화한다.

## 2. 팀원별 인터페이스 책임

| 담당 | 이름 | 모듈 | 인터페이스 책임 |
|---|---|---|---|
| A | 윤현수 | Mission Manager | 작업 상태, 최적화 요청, 계획 적용, 주행 실행 관리 |
| B | 정지호 | Global Planner Research | 전역 플래너 설정·선정 결과 제공 |
| C | 이현수 | Route Optimizer | 계획 경로 비용 계산, 방문 순서, 재계획 결과 |
| C | 이현수 | Robot Bringup | 센서·드라이버·TF·기본 구동환경 제공 |
| D | 홍근태 | AMR Navigation | Nav2·AMCL, 목표 이동, 주행 결과, 제어기 설정 |
| E | 강연주 | Web Control | 작업 요청, 인계 확인, 관제, 실험 데이터 저장 |

### 2.1. 핵심 책임 경계

**A — 상태·실행 관리**

- Job·TaskStep·Mission 상태 전이 관리
- 계획 계산 요청 및 결과 검증
- 최신 계획 버전 확정
- 주행 실행 요청
- 인계 완료 및 전체 미션 완료 판정

**B — 전역 플래너 연구**

- A*·Dijkstra 비교 실험
- 플래너 설정 및 선정 근거 제공
- D의 Nav2 설정과 C의 비용 계산 기준 검증

**C — 최적화·하드웨어**

- 방문 순서 계산과 재계획 결과 제공
- 계획 경로 기반 이동 비용표 관리
- 센서·드라이버·기본 Bringup 제공

**D — 실제 주행 관리**

- Nav2·AMCL 및 Controller 관리
- 실제 주행 목표의 실행 및 결과 제공
- Navigation Readiness 관리

**E — 웹·데이터**

- 작업·인계 요청 전달
- A가 결정한 상태 표시
- B·C·D 실험 결과 저장 및 시각화

## 3. 모듈 간 통신 개요

### 3.1. 주요 계약

| 연결 | 목적 | 우선 검토 방식 | 상태 |
|---|---|---|---|
| E → A | 작업 등록·실행·인계 요청 | E 백엔드 → A HTTP/JSON | 공항 단일 주문 SIM |
| A → C | 방문 순서·재계획 계산 | `OptimizeRoute` Service | [확정] |
| C → A | 계획 후보·예상 비용·기준 버전 반환 | 요청·응답 | [확정: 데이터 방향] |
| A → D | 목표 지점 이동 요청 | Nav2 표준 Action 또는 얇은 Navigation Adapter | [설계 후보] |
| D → A | 주행 상태·성공·실패·취소 | Action 피드백 및 결과 | [확정: 데이터 방향] |
| C → Nav2 | 지점 간 계획 경로 계산 | `ComputePathToPose` Action | [설계 후보] |
| B ↔ D | 전역 플래너 실험 및 설정 적용 | Nav2 설정·실험 도구 | [확정: 협업 책임] |
| B → C | 플래너 설정·계산 기준 제공 | 설정 파일·메타데이터 | [확정: 협업 책임] |
| C Bringup → D | 센서·TF·구동환경 제공 | ROS2 표준 Topic·Launch | [확정: 책임 방향] |
| A → E | 미션 상태·오류·계획 제공 | E가 A 상태를 조회 | 공항 단일 주문 SIM |
| B·C·D → E | 실험 결과 | JSON·CSV·SQLite 연동 | [설계 후보] |

위 통신 방식은 패키지 사이에 반드시 별도의 중계 노드가 있어야 한다는 의미가 아니다.

표준 Nav2 Action을 직접 사용하는 방식이 더 간단하면 이를 우선 검토한다.

### 3.2. 데이터 흐름

```text
[E] Web / Order API
    │
    │ 작업 등록
    ▼
[A] Mission Manager
    │
    │ 방문 순서 계산 요청
    ▼
[C] Route Optimizer
    │
    ├── [D] Nav2 Planner
    │       └── ComputePathToPose
    │
    │ 계산된 방문 순서 반환
    ▼
[A] Mission Manager
    │
    │ 이동 요청
    ▼
[D] AMR Navigation
    │
    ├── Nav2 / AMCL
    └── [C] Robot Bringup 환경 활용
    │
    │ 이동 결과
    ▼
[A] Mission Manager
    │
    │ 인계 대기 상태 제공
    ▼
[E] Web / Operator
    │
    │ 인계 완료 요청
    ▼
[A] Mission Manager
    │
    ├── 다음 작업 실행
    └── 모든 작업 완료 후 HOME 복귀
```

## 4. 공통 데이터 모델

다음 모델은 시스템 내부에서 일관되게 사용해야 할 개념과 필수 정보다.

이 표에 적힌 필드명이 곧바로 확정된 `.msg`, `.srv`, Python 클래스 또는 JSON 속성명이라는 의미는 아니다.

### 4.1. Job

물류 업무 단위.

| 정보 | 의미 |
|---|---|
| Job ID | 개별 업무 식별자 |
| Pickup Waypoint | 물품 수거 지점 |
| Dropoff Waypoint | 물품 전달 지점 |
| Job Status | 업무 진행 상태 |
| TaskStep 목록 | 업무를 구성하는 실행 단계 |

예시: `JOB-002: B → C`

### 4.2. TaskStep

실제 수행할 수거 또는 전달 단계.

| 정보 | 의미 |
|---|---|
| TaskStep ID | 작업 단계 식별자 |
| Job ID | 소속 업무 |
| Step Type | PICKUP / DROPOFF |
| Waypoint ID | 수행 위치 |
| Prerequisites | 선행 완료 조건 |
| Step Status | 단계별 진행 상태 |

예시:

- `JOB-002-PICKUP`: B 수거
- `JOB-002-DROPOFF`: C 전달

DROPOFF 단계는 PICKUP 단계가 완료된 뒤에만 실행 가능하다.

### 4.3. Waypoint

지도에 등록한 방문 지점.

| 정보 | 의미 |
|---|---|
| Waypoint ID | HOME, A, B, C, D |
| Pose | 지도 좌표 및 목표 방향 |
| Frame | 좌표 기준 프레임 |
| Map Version | 지점 좌표가 속하는 지도 버전 |

기본 Pose는 ROS2 표준 형식을 우선 사용한다.

### 4.4. Mission

전체 물류 작업을 관리하는 실행 단위.

| 정보 | 의미 |
|---|---|
| Mission ID | 미션 식별자 |
| Job 목록 | 실행 대상 업무 |
| Mission Status | 전체 미션 상태 |
| Current TaskStep | 현재 실행 단계 |
| Active Plan Version | 현재 승인된 계획 버전 |

Mission의 상태는 개별 TaskStep 및 Nav2 주행 상태와 구분한다.

### 4.5. RoutePlan

C가 계산하고 A가 검증·적용하는 방문 계획.

| 정보 | 의미 |
|---|---|
| Plan ID | 계획 식별자 |
| Base Plan Version | 계산의 기준이 된 계획 버전 |
| Ordered Tasks / Waypoints | 계산된 방문 순서 |
| Estimated Cost | 예상 계획 이동 비용 |
| Costmap / Map Version | 경로 비용 산출 기준 |
| Planner Configuration | 사용한 플래너 기준 |
| Calculation Status | 계산 성공·실패 |

**버전 관리 원칙**

- C는 계산에 사용한 기준 계획 버전을 반환한다.
- A는 계산 결과가 현재 미션 상태와 일치하는지 검사한다.
- A가 계획을 승인·적용하면서 활성 계획 버전을 관리한다.
- 오래된 기준 버전의 결과는 자동 적용하지 않는다.

C가 반환한 기준 버전과 A의 활성 버전을 동일한 의미로 혼동하지 않는다.

### 4.6. RobotStatus

실제 로봇의 실행 상태와 준비 상태를 표현한다.

| 정보 | 의미 |
|---|---|
| Robot Pose | 현재 위치 및 방향 |
| Navigation Status | 목표 이동 상태 |
| Connectivity | 연결 상태 |
| Hardware Readiness | 센서·Bringup 준비 상태 |
| Navigation Readiness | AMCL·Nav2 준비 상태 |
| Error / Failure Reason | 오류 및 주행 실패 사유 |
| Timestamp | 상태가 측정된 시각 |

RobotStatus의 실제 Topic 구조 및 배포 방식은 [설계 후보]다.

C는 하드웨어 관련 원천 상태를 제공하고, D는 주행 상태를 제공한다.

A가 필요한 준비 상태를 종합하여 미션 실행 허용 여부를 결정한다.

### 4.7. ExperimentResult

알고리즘 비교 실험의 결과.

| 정보 | 의미 |
|---|---|
| `experiment_id` | 실험 ID |
| `scenario_id` | 실험 시나리오 |
| `run_mode` | MOCK / SIM / REAL |
| `algorithm` | 적용 알고리즘 |
| `config_version` | 설정 버전 |
| `map_version` | 지도 버전 |
| `planner_id` | 플래너 설정 ID |
| `controller_id` | 제어기 설정 ID |
| `planned_distance` | 계획 경로 길이 |
| `actual_distance` | 실제 주행 거리 |
| `planning_time` | 계산 시간 |
| `execution_time` | 주행 시간 |
| `goal_success` | 목표 도달 결과 |
| `mission_success` | 미션 완료 결과 |
| `failure_reason` | 실패 원인 |

ExperimentResult는 우선 JSON·CSV·SQLite 기반으로 관리한다.

명확한 ROS2 통신 요구가 없다면 별도 사용자 정의 ROS2 메시지로 만들지 않는다.

## 5. 작업 상태 및 완료 이벤트 계약

### 5.1. TaskStep 상태

| 상태 | 의미 |
|---|---|
| `PENDING` | 등록됨 |
| `READY` | 실행 조건 충족 |
| `IN_PROGRESS` | 실행 중 |
| `WAITING_CONFIRMATION` | 물품 인계 대기 |
| `COMPLETED` | 작업자 확인 및 완료 처리 |
| `FAILED` | 실행 실패 |
| `CANCELLED` | 취소 |

Mission 상태, TaskStep 상태, Navigation 상태는 동일한 상태 열거형으로 통합하지 않는다.

### 5.2. 인계 완료 판정

1. D가 목표 도착 결과를 A에 반환한다.
2. A는 현재 단계가 물품 인계를 요구하는지 검사한다.
3. A는 해당 단계를 `WAITING_CONFIRMATION`으로 전환한다.
4. E에서 작업자 확인 요청을 전달한다.
5. A는 요청 대상, 현재 단계, 기존 처리 여부를 검사한다.
6. 유효한 요청일 경우에만 `COMPLETED`로 전환한다.
7. 다음 실행 가능한 작업을 결정한다.

**완료 조건**

- 목표 도착만으로 TaskStep을 완료 처리하지 않는다.
- 같은 인계 요청이 중복 전달되어도 작업을 두 번 실행하지 않는다.
- 이전 TaskStep의 완료 요청이 현재 작업에 적용되지 않도록 한다.
- HOME 최종 하역 확인이 필요한 경우 이 단계까지 완료해야 Mission을 종료한다.

### 5.3. 중복 요청 처리

**[확정]** E는 사용자 조작마다 고유한 `event_id`를 발급하고 `mission_id`, `step_id`와 함께 전달한다. 재전송 시 세 값을 유지한다. A는 미션별 이벤트 원장에서 같은 이벤트·단계의 최초 결과(`accepted` 또는 `rejected`)를 재사용한다. 같은 키를 다른 단계에 쓰면 `conflict`를 반환한다. 새 이벤트도 현재 인계 대기 단계에만 적용한다. 거부 후 실제로 다시 확인한 조작은 새 이벤트다.

**확정된 계약 / A의 영속 처리 MOCK 검증 완료.** E는 발신 이벤트를 기록한 뒤 전송하고 A의 결과를 받아 표시한다. 타임아웃은 결과 미확인 상태다. A가 처리한 직후 응답이 유실되거나 E의 DB 기록이 실패하면 같은 키로 재조회·재전송한다. A는 ACK 전에 상태 전이와 처리 결과를 함께 복구 가능하게 저장해야 한다. E의 기록만으로 미션 상태를 확정할 수 없다. 복구 완료 시험은 처리 직전·직후 재시작과 응답 유실을 주입해 완료 전이 1회 및 동일 결과 복원을 확인한다. A는 `database_path`에 파일을 지정하면 SQLite로 원장을 복구한다. 기본 `:memory:`는 프로세스 내 테스트용이다. 웹 전송 및 E와의 실제 ACK 복구 통합은 검증 대기다. [A 실행 안내](../ros2_ws/src/mission_manager/README.md)

## 6. A ↔ C — 최적화 및 재계획 계약

### 6.1. A → C 계산 요청

**목적**

현재 작업 상태를 기준으로 유효한 방문 순서를 계산한다.

**필수 정보**

- Mission ID
- 기준 Plan Version
- 현재 또는 적용 기준 위치
- 완료된 TaskStep 목록
- 진행 중인 TaskStep
- 실행 대기 중인 TaskStep
- 새로 접수된 작업
- 작업 선후 관계
- 지도·비용표 기준 정보

신규 주문이 없는 최초 계획 요청에도 동일한 기본 계약을 사용할 수 있다.

### 6.2. C → A 계산 응답

**필수 정보**

- 계산 성공·실패
- 기준 Plan Version
- 최적화 방식
- 방문 순서
- 예상 계획 이동 비용
- 반영한 TaskStep 목록
- 계산 시 사용한 비용표·설정 버전
- 실패 시 사유

C는 계산 결과를 반환할 뿐 미션 상태를 직접 변경하거나 주행을 시작하지 않는다.

### 6.3. A의 적용 검증

A는 다음 사항을 확인한다.

- 반환된 기준 Plan Version이 현재 상태와 일치하는가?
- 완료된 작업이 다시 포함되지 않았는가?
- 진행 중인 작업이 보호되고 있는가?
- 수거·전달 선후 관계가 유지되는가?
- 이동 불가능한 구간이 포함되지 않았는가?
- 재계획 적용 시점이 안전한가?

검증 결과가 유효할 때만 활성 계획으로 승인한다.

### 6.4. A↔C 서비스와 적용 규칙

**[확정]** A는 `logistics_msgs/srv/OptimizeRoute`의 클라이언트, C는 서버다. 기본 상대 서비스명은 `optimize_route`이며 ROS 네임스페이스로 배치한다. [서비스 선언](../ros2_ws/src/logistics_msgs/srv/OptimizeRoute.srv)과 [단계 선언](../ros2_ws/src/logistics_msgs/msg/TaskStep.msg)이 필드 및 직렬화 타입의 기준이다. A 클라이언트와 C 테스트 대역의 DDS 왕복은 검증했다. C 실제 서버와의 연동은 통합 검증 대상이다.

- Job은 주문, TaskStep은 주문의 수거·전달 단계, Waypoint는 물리적 위치다. 여러 단계가 한 지점을 공유할 수 있다. `step_id`는 미션 안에서 고유하다. A는 등록 입력과 요청 메시지를 복사하고 중복 단계, 미등록 선행 단계, 자기 참조·순환, 같은 Job의 수거를 선행 조건에서 누락한 전달을 거부한다.
- A는 미션 인스턴스별로 증가하는 `request_id`와 현재 활성 버전 `base_version`을 보낸다. 복구 시 같은 미션 ID를 재사용하려면 발급 번호와 활성 버전을 복원해야 한다. 요청에는 현재 단계 ID, 완료 ID, 신규 주문을 포함한 전체 대기 단계, 출발 Waypoint, 비용표 버전이 있다. 현재 작업 중이면 그 작업의 도착 지점이 출발점이다.
- C는 요청·미션 ID와 기준 계획 버전을 그대로 돌려준다. 성공 시 실제 사용한 `cost_revision`, 방법, 계획 거리(m), **대기 단계 ID의 전체 순열**을 반환한다. 도달 불가·계산 실패 시 실패와 사유를 반환한다. C는 후보 계산만 담당한다.
- A의 활성 계획 버전은 0에서 시작해 후보를 검증하고 활성 계획으로 채택할 때마다 1씩 증가한다. 요청·계산·거부·단계 완료 자체는 버전을 올리지 않는다. 신규 주문이나 대기 집합 변경, 출발점 변경에 따른 새 요청, 비용표 교체는 이전 후보를 만료시킨다. 마지막 요청 ID, 기준 버전, 비용표, 남은 단계의 완전성 및 순서를 모두 검사한다.
- 현재 작업 중에 받은 후보는 현재 단계 인계 후 같은 응답을 재검증한다. 그동안 최신성이 사라졌으면 다시 요청한다. 현재 단계의 예상된 완료는 요청 시 이미 제외한 단계이므로 그 자체로 후보를 만료시키지 않는다. MOCK에서는 호출자가 응답을 보관한다.
- 비용표 생성·발급·갱신의 단일 담당은 C다. B는 플래너 설정·버전, D는 지도·주행 설정을 제공한다. C는 지도·지점·플래너·Costmap 기준과 방향별 비용/도달 가능성을 묶어 불변 스냅샷으로 관리한다. 동일 스냅샷에는 동일한 비어 있지 않은 버전, 내용 또는 산출 기준이 바뀌면 새 버전을 사용한다. A는 C가 알린 사용 가능 버전을 기준으로 이전 응답을 거부한다. 교체 통지·저장 방식과 실제 비용 계산은 Phase 1에서 구현한다.

## 7. A ↔ D — 주행 실행 계약

### 7.1. A → D 이동 요청

**목적**

승인된 방문 계획의 다음 목표를 실제 로봇에서 수행한다.

**논리적 입력**

- Mission ID
- 실행 중인 Plan Version
- 실행 요청 식별자
- 목표 Waypoint
- 목표 Pose
- 해당 목표와 연결된 TaskStep

이 목록은 Mission Manager의 논리적 실행 컨텍스트이며 Nav2 `NavigateToPose` Action의 실제 Goal 필드와 동일하지 않다.

표준 Action이 제공하지 않는 정보는 A의 내부 상태로 유지하거나 필요한 범위에서 별도 계약을 구성한다.

### 7.2. D → A 주행 결과

**필수 의미**

- 목표 실행 요청의 식별 가능성
- 현재 주행 중 여부
- 목표 도달 성공
- 목표 도달 실패
- 취소 또는 중단 결과
- 오류 원인
- 필요한 경우 로봇 위치·준비 상태

D는 목표 도달 성공 여부를 반환하며, 물품 인계 완료까지 결정하지 않는다.

### 7.3. Nav2 표준 인터페이스

우선 다음 표준 Action을 활용한다.

- `NavigateToPose`: 일반적인 작업 지점 이동
- `ComputePathToPose`: 계획 경로 및 경로 비용 계산
- `FollowPath`: 동일한 경로를 사용하는 제어기 비교 실험

`FollowWaypoints`는 검토할 수 있으나 초기 물류 작업에서는 지점 도착과 인계 확인을 분리해야 하므로 `NavigateToPose` 기반 실행을 우선한다.

별도의 Navigation Adapter가 필요한 경우에도 기존 Nav2 기능을 중복 구현하지 않는다.

A의 Python 경계, UUID·시도 대응 및 별도 프로세스 검증 계획은 [A↔D 인수인계](INTEGRATION_A_D_HANDOFF.md)를 참고한다.

### 7.4. 주행 취소 및 실패

- 신규 주문이 발생했다는 이유만으로 진행 중인 목표를 즉시 취소하지 않는다.
- 기본 동적 재계획은 현재 작업 완료 후 적용한다.
- 안전 관련 중단은 일반 재계획 정책보다 우선한다.
- Nav2 실패 결과를 Mission 완료로 해석하지 않는다.
- 타임아웃과 통신 단절은 실제 성공·실패 여부를 확인하기 전까지 불확실한 상태로 취급한다.
- 실패 후 재시도 또는 복구의 구체적 정책은 별도 검증을 통해 확정한다.

## 8. C ↔ Nav2 — 계획 경로 비용 계산 계약

### 8.1. 비용 계산 주체

C의 `route_optimizer`는 D가 운영하는 Nav2 Planner 환경에서 계획 경로를 요청한다.

표준 `ComputePathToPose` Action을 직접 호출하는 방식을 우선 검토한다.

### 8.2. 비용 계산 입력

- 출발 지점 Pose
- 목표 지점 Pose
- 출발 자세 사용 여부
- 적용 Planner ID
- 지도 및 관련 설정 기준

고정 지점 사이의 비용 계산에서는 명시적인 시작 Pose를 사용하도록 `use_start` 설정을 확인한다.

ROS2 Jazzy의 `nav2_msgs/action/ComputePathToPose`에는 `goal`, `start`, `planner_id`, `use_start` Goal 필드가 있다. 명시적 시작 Pose로 지점 간 비용을 계산할 때 `start`와 `use_start: true`를 사용하며, 실행 서버·플래너 ID의 실제 가용성은 개발환경에서 확인한다.

### 8.3. 계산 결과

- 계획 경로 생성 성공 여부
- `nav_msgs/Path`
- 실패 시 상태·원인
- 경로 계산에 사용한 설정 정보

계획 경로의 연속 Pose 사이 거리를 합산해 계획 이동 비용을 계산한다.

이 값은 실제 로봇의 주행 거리가 아니다.

### 8.4. 비용표 유효성

다음 조건이 변경되면 비용표를 재검증한다.

- 지도 버전
- 작업 지점 좌표
- Costmap 설정
- 전역 Planner 설정
- 로봇 Footprint 등 경로 가능성에 영향을 주는 설정

방향에 따라 비용이 다를 수 있으므로 `A → B`와 `B → A`를 별도로 계산한다.

경로를 생성할 수 없는 경우 임의의 정상 거리로 대체하지 않는다.

## 9. B ↔ C·D — 전역 플래너 협업 계약

### 9.1. B → D

B는 A*·Dijkstra 비교 연구를 통해 검증한 플래너 설정과 선정 근거를 D에게 제공한다.

D는 실제 Nav2 실행 환경에 해당 설정을 적용하고 주행 검증에 참여한다.

### 9.2. B → C

B는 플래너 비교 조건과 선정된 설정을 C에게 제공한다.

C는 계획 이동 비용표 생성 시 동일한 플래너 기준을 사용한다.

### 9.3. 변경 관리

플래너 변경으로 기존 비용표의 경로 길이나 도달 가능성이 달라질 수 있으므로 B·C·D는 설정 버전을 공유한다.

플래너 설정 변경은 실험 결과 및 비용표 유효성에 영향을 주는 변경으로 취급한다.

## 11. E ↔ A — 웹 관제 및 작업 요청

### 11.1. E → A

웹에서 다음 요청을 전달한다.

- 신규 Job 등록
- 물품 인계 완료 확인
- 미션 실행 요청
- 승인된 범위의 운영 명령
- 현재 미션 상태 조회

미션 취소·정지·재개 등의 제어 기능은 실제 안전 정책과 구현 범위를 확인한 뒤 제공한다.

### 11.2. A → E

A가 관리하는 다음 정보를 제공한다.

- Mission 상태
- Job·TaskStep 상태
- 활성 RoutePlan
- 현재 실행 지점
- 물품 인계 대기 상태
- 미션 오류 및 완료 결과
- 재계획 적용 이력

### 11.3. 웹↔ROS2 연결 방식

공항 SIM 주문 한 건에는 E의 FastAPI 백엔드가 A의 로컬 HTTP/JSON 게이트웨이를 호출한다. A가 같은 실행기에서 ROS2 서비스와 SQLite를 관리한다. E는 기존 웹 API로 주문과 사람의 인계를 받고 A 상태를 화면에 표시한다. 네 가지 호출과 응답, 재전송, 실행 조건은 [A↔E SIM 계약](../ros2_ws/src/mission_manager/WEB_SIM.md)을 따른다. 실차 배포와 센서 데이터 전송은 별도 결정 대상이다.

### 11.4. DB와 상태 관리

E의 SQLite는 주문·이력·실험 결과 저장에 사용할 수 있다.

단, 미션의 실행 상태를 변경하는 최종 권한은 A의 Mission Manager에 둔다.

서버나 ROS2 노드 재시작 시 DB 기록과 실제 미션 상태를 어떻게 복원할지는 별도의 계약으로 확정한다.

## 12. ROS2 QoS 및 상태 전달

### 12.1. 기본 원칙

- 센서 Topic은 실제 드라이버의 QoS 호환성을 우선한다.
- 상태 정보와 고주기 센서 정보를 동일한 QoS로 일괄 설정하지 않는다.
- Service·Action과 Topic을 목적에 맞게 구분한다.
- 늦게 연결된 구독자에게 마지막 상태를 제공할 필요가 있는지 별도로 판단한다.

### 12.2. QoS 선택 후보

| 데이터 | 검토 기준 |
|---|---|
| LiDAR·고주기 센서 | 기존 센서 Publisher와의 호환성 |
| 미션 상태 변경 이벤트 | 손실 허용 여부와 순서·중복 처리 |
| 현재 상태 스냅샷 | Reliable 및 필요한 경우 Transient Local 검토 |
| 주행 진행 피드백 | 최신성·전송 주기·손실 허용 범위 |
| 정적 설정·지점 데이터 | 상태 재전달 및 버전 관리 필요성 |

`Transient Local`은 필요한 상태 스냅샷에 한하여 검토한다.

모든 Topic에 적용하거나 센서 데이터 전달 안정성을 자동 보장하는 수단으로 취급하지 않는다.

QoS 호환성은 실제 Publisher·Subscriber에서 검증한다.

## 13. 오류·타임아웃·중복 요청 처리

### 13.1. 공통 오류 원칙

- 요청 실패를 정상 완료로 처리하지 않는다.
- 요청 타임아웃이 실제 작업 실패를 의미한다고 단정하지 않는다.
- 같은 작업을 재시도할 때 중복 실행 위험을 확인한다.
- 오류 응답에는 가능한 한 요청을 식별할 정보와 실패 원인을 포함한다.
- 로봇이 실행 중인지 불명확한 경우 무조건 동일한 이동 명령을 다시 보내지 않는다.

### 13.2. 주요 오류

| 오류 | 처리 책임 |
|---|---|
| 유효하지 않은 Job | A |
| 선후 관계 위반 | A·C |
| 방문 순서 계산 실패 | C, A가 미션 상태 관리 |
| 경로 생성 실패 | D·C, B가 플래너 분석 지원 |
| Nav2 목표 이동 실패 | D, A가 미션 상태 관리 |
| 센서·드라이버 장애 | C |
| AMCL·Nav2 준비 실패 | D |
| 물품 인계 요청 오류 | A·E |
| 계획 버전 불일치 | A |
| 웹 연결 단절 | E·A, 주행 안전은 C·D와 검증 |

### 13.3. 타임아웃과 재시도

각 요청의 타임아웃, 재시도 횟수 및 취소 정책은 실제 실행 환경과 시험 결과를 기준으로 결정한다.

임의의 수치를 확정값으로 사용하지 않는다.

Priority P0에서는 계산 실패·주행 실패·인계 지연이 발생해도 상태가 잘못 완료 처리되지 않도록 한다.

## 14. MOCK / SIM / REAL 인터페이스

상위 미션 로직이 환경별 구현 차이를 최소화하도록 다음 원칙을 적용한다.

### MOCK

- 가상 로봇 상태 및 목표 이동 결과 제공
- Job·TaskStep 상태 머신 검증
- 재계획 요청과 결과 검증
- 웹 요청·인계 확인 E2E 검증

### SIM

- Gazebo Harmonic 및 ROS2 Jazzy·Nav2 시뮬레이션 사용
- 경로 계산과 주행 기능 검증
- 시뮬레이션 데이터로 실행 결과 기록

### REAL

- TurtleBot3 실제 센서와 구동환경 사용
- TF·Odometry·AMCL·Nav2 상태 확인
- 주행 거리·시간·성공률 실측
- 비상정지 및 안전 복구 절차 검증

`use_sim_time`은 ROS 시간 기준을 선택하는 설정이지 네트워크나 DDS를 격리하는 기능이 아니다.

SIM과 REAL의 통신 및 실행 환경이 혼합되지 않도록 별도 검증한다.

## 15. 인터페이스 검증 기준

| 검증 항목 | 완료 조건 |
|---|---|
| E → A 신규 주문 | 유효한 Job으로 등록되고 중복 처리되지 않음 |
| A → C 최적화 | 선후 관계를 만족하는 방문 순서 반환 |
| C → A 결과 | 기준 버전·예상 비용·상태 정보 포함 |
| A → D 주행 | 승인된 목표만 실행 요청 |
| D → A 주행 결과 | 성공·실패·취소를 구분 |
| E → A 인계 확인 | 현재 대기 중인 TaskStep만 완료 |
| C → Nav2 비용표 | 계획 경로 기반 비용 계산 및 버전 기록 |
| B·C·D 실험 | 동일한 기준으로 설정·결과 기록 |
| C Bringup → D | 실제 센서·통신·TF 환경 정상 검증 |
| 전체 재계획 | 진행 중인 작업 보호 및 최신 계획 적용 |
| HOME 최종 처리 | 최종 인계 후 전체 미션 완료 판정 |

실제 검증을 수행하지 않은 항목은 완료로 표시하지 않는다.
